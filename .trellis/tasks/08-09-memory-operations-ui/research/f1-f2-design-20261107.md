### Recommended smallest cache

Cache **successfully verified schema/implementation support**, owned by the existing `MemoryEngine` lifetime. Keep `build_taki_compatibility_manifest` available as the uncached inspector for independent/admin callers.

Cache identity:

1. Backend instance.
2. Effective authenticated schema qualifier.
3. Memory-store and tenant-extension instances.
4. Current Alembic revision set.
5. Provider lineage.

Use the existing schema-local Alembic metadata; it already has a schema-specific version table. This avoids inventing a generation table or invalidation service. [source alembic/env.py:170]

Keep these observations live on every cached-manifest access:

- Authentication and tenant resolution.
- Cheap capability descriptors.
- The existing provider-lineage read.
- One Alembic-revision read, on the same acquisition.

The revision read is justified by the existing external migration command, which cannot call an engine-local hook. It is a cache key, not a replacement for the full schema inspection.

If revision metadata cannot be read, **bypass caching and retain the existing inspector’s result**. Do not turn a missing cache key into a new capability refusal.

Cache only a fully successful inventory initially. Unsupported or failed probes remain uncached because the current inspector can classify transient probe failures as unsupported; retaining those results would make recovery sticky. Optional capabilities keep their independent outcomes. [source engine/taki_compatibility.py:449]

#### Invalidation

- Clear on engine initialization/reinitialization and close.
- Invalidate the affected schema **before** `DefaultExtensionContext.run_migration` starts and again in `finally`, including extension-table provisioning.
- Disable cache publication while that migration hook is active.
- Backend/store/tenant replacement or effective-schema change causes a key miss.
- Changed Alembic revisions or lineage cause a key miss and full inspection.
- Failed live lineage/database observation discards reuse eligibility and preserves the current failure result.
- Supported offline restore obtains a fresh cache through process restart.
- Normal data changes do not invalidate the inventory.

Use a small generation counter solely to prevent an inspection started before invalidation from repopulating the cache afterward. Do not add a TTL, background refresher, retry framework or request coalescer.

**In-flight behavior:** invalidation does not cancel or replay dispatched operations. An already-running inspection can complete under existing behavior, but cannot publish its result into an invalidated cache. Existing SQL transactions, namespace checks, CAS and writer fences govern operations that already passed admission. Preserve their actual success, refusal or unknown-write outcome.

Uncoordinated same-revision DDL is a limitation: neither Alembic identity nor a process-local hook detects an administrator manually disabling a trigger. Such administration requires restart/invalidation; this design does not claim continuous schema auditing.

## Part 2 — Core admission reuse

### Contract versus implementation habit

No inspected specification requires **health → API version → compatibility** on every synchronization.

The actual contracts include:

> “Require build … `application_state` version `1.0.0`, and the actual client methods.”  
> [source .trellis/spec/backend/hindsight-application-runtime.md:45]

> “Recovery order is authenticated lineage/Bank admission, complete first pull … then second pull and local confirmation.”  
> [source .trellis/spec/backend/memory-replica-sync.md:292]

> “Ordinary guards then reread current identity plus the original connection/secret/template/Bank/cancellation checks.”  
> [source .trellis/spec/backend/memory-authority-validation.md:38]

Explicit connection revalidation has a stronger, named requirement:

> “`validating`: `admitHindsightApplication` with the epoch’s lineage …”  
> [source .trellis/spec/backend/memory-hindsight-lifecycle.md:122]

Therefore, retain full fresh admission for explicit `connection.revalidate`. Repetition inside every ordinary sync is an implementation choice. [source memory/hindsight/hindsight-application-sync-runner.ts:118]

### Important limitation: historical namespaces are not current-provider proof

A zero-network reuse design cannot rely solely on D77 page namespace validation:

- `ApplicationStateService.get_changes` does not request a live-Bank check. [source engine/application_state/service.py:183]
- `snapshot.changes` reads the addressed historical application namespace and returns `namespace=store.namespace`. [source engine/application_state/snapshot.py:360]
- Core correctly validates that response against the requested namespace, but this does not establish the endpoint’s **current provider lineage**. [source memory/hindsight/hindsight-application-client.ts:179]

Do not describe those checks as equivalent to the current manifest-lineage comparison.

**Recommendation:** retain **one compatibility read before each independent synchronization**, while reusing persisted admission evidence to skip health and API-version probes. Reflect and Pending recovery reuse the synchronization’s admitted result.

This removes repeated full admission without adding a new identity endpoint, scanning the native journal merely to discover identity, or weakening the lineage guarantee. It deliberately does **not** promise zero admission-related requests per sync.

### Reuse the existing persisted evidence

Continue using:

`(authorityEpochId, configFingerprint) → verified manifest, admittedAt`

The repository already validates the evidence hash, stored lineage and epoch/provider association. No SQLite schema change or second manifest store is needed. [source db/hindsight-runtime-admission-repo.ts:26]

The configuration fingerprint already includes endpoint, deployment mode, request/setup timeouts, desired template revision, model settings and secret marker. Reuse it unchanged. [source memory/hindsight/hindsight-compatibility-service.ts:118]

Use one admission resolver shared by the composed runtime:

- **Cold/new runtime, missing evidence or invalidated online admission:** perform the existing three calls, check expected lineage, then save through the existing repository.
- **Warm synchronization:** read persisted evidence, perform one authenticated compatibility request, retain the existing capability/client-method and lineage checks, and reuse the admitted evidence when unchanged.
- **Changed manifest:** discard warm reuse; perform full admission before continuing or preserve the existing unsupported/mismatch refusal.
- **Reflect following successful synchronization:** use its admitted manifest and independently check guarded-Reflect support; do not repeat admission.
- **D77 Pending recovery:** obtain native-result support from the admitted manifest. D77 admission already requires the supported G1 contract. Preserve the legacy runner’s independent capability path when no application-admission resolver is supplied.
- **Capability snapshots/degraded reads:** retain last-verified persisted evidence. Its existence does not assert current network health.

Only small runtime-local reuse state is needed: whether full admission is required and an invalidation generation. The persisted manifest remains the evidence source.

#### Invalidation and in-flight behavior

| Trigger | Required behavior |
|---|---|
| Endpoint/configuration/API-key marker change or disable | Existing connection guard refuses/degrades the old runtime as specified. The new identity cannot reuse its predecessor’s evidence. |
| Authority epoch or lineage change | Existing authority guard refuses; evidence cannot cross epochs. |
| Availability, authentication or compatibility failure | Require full admission on the next online attempt. Preserve historical evidence for supported replica fallback. |
| Namespace/lineage mismatch | Invalidate online reuse and preserve the original refusal. Never convert it to an empty result. |
| Core restart/rebind | Start online admission cold; persisted evidence remains usable as last-verified capability evidence. |
| Native restart | No process-incarnation identifier is exposed through the current client contract. The mandatory compatibility read detects changed lineage/build/support; transport failures also invalidate. A same-build/same-lineage restart is not separately identifiable. |
| Caller cancellation | Preserve cancellation; do not erase valid historical evidence merely because a caller cancelled. |
| Old response completes after invalidation | Recheck the existing request/connection/cancellation guards. Do not let that response mark the invalidated generation reusable or overwrite evidence for another identity. No automatic write replay. |

Observe availability failures at the existing common client error boundary, rather than adding separate transport policies to each consumer. Observe typed D77 refusals where the existing application caller already constructs them. These callbacks only invalidate reuse; they do not reinterpret operation results. [source memory/hindsight/hindsight-client.ts:212] [source memory/hindsight/hindsight-application-client.ts:174]

2. Fresh snapshot scope additionally checks the native snapshot’s Bank and provider lineage. [source memory/hindsight/hindsight-application-sync-runner.ts:195]
3. Every returned D77 scope and every SQLite publication retain their current checks. [source memory/hindsight/hindsight-application-sync-runner.ts:99] [source memory/hindsight/hindsight-application-sync-runner.ts:213]

## Implementation plan

### Failure modes to establish first

Before changing tests or implementation, establish these expected behaviors:

1. **Warm authentication failure:** cached schema/admission must not bypass a changed or invalid key.
2. **Schema isolation:** one engine serving two schema qualifiers must not reuse one schema’s support for the other.
3. **D78 appearance:** an initially unsupported schema becomes supported after the real migration hook; no cached absence bypasses maintenance coordination.
4. **Migration failure/in-flight inspection:** invalidated inspections cannot repopulate reusable cache state; actual errors remain errors.
5. **External migration:** changed Alembic revisions invalidate the cached inventory.
6. **Lineage changes with historical D77 rows still readable:** synchronization refuses before trusting those rows.
7. **Availability recovery:** last-verified evidence remains available for permitted degraded reads, while the next online attempt performs fresh admission.
8. **Epoch/configuration/cancellation changes during admission:** no late save, publication or native dispatch.
9. **Guarded Reflect unavailable:** reuse never enables unguarded Reflect.
10. **G1 versus D77 independence:** legacy recovery retains its existing capability behavior; failed negotiation never becomes `nativeResultSupported=false` success.
11. **Native restart:** changed lineage/build is detected; same-identity restart does not corrupt reuse.
12. **Slow durable writes:** deadline expiry preserves real Pending/unknown outcomes and original request identities.
13. **Backup with active work:** preserve the 30 s refusal; retry only after actual drain. Faster nominal runs must not weaken this case.
