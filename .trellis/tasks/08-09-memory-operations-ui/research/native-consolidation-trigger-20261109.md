### Q1. When Native consolidation runs

**Ordinary Native execution is immediate admission to a durable background queue, not synchronous consolidation before retain returns.** The post-fact-insert helper submits consolidation when both observations and auto-consolidation are enabled. The default engine uses a broker task backend; an explicitly supplied `SyncTaskBackend` executes the same submitted task inline for embedded/test use. These are distinct execution modes. [source hindsight_api/engine/memory_engine.py:5048] [source hindsight_api/engine/memory_engine.py:5063] [source hindsight_api/engine/memory_engine.py:1313] [source hindsight_api/engine/memory_engine.py:17694]

| Trigger / timing | Actual behavior and boundary |
| --- | --- |
| After retain / fact import | Fact insertion invokes the existing post-insert chain; consolidation admission is gated by resolved Bank settings. Submission failures are logged without converting an already successful fact insertion into failure; the recovery sweep can later recover eligible unscheduled facts. [source hindsight_api/engine/memory_engine.py:5048] [source hindsight_api/engine/memory_engine.py:5057] [source hindsight_api/engine/maintenance.py:8] |
| Pending-job coalescing | Full-Bank submits deduplicate against an existing **unscoped pending** consolidation for that Bank. A processing job does not swallow a new pending job. Explicit scoped submissions bypass Bank deduplication. This is queue coalescing, not a configured debounce window. [source hindsight_api/engine/memory_engine.py:18228] [source hindsight_api/engine/memory_engine.py:17589] [source hindsight_api/engine/memory_engine.py:17601] |
| Batched execution | The worker loads bounded fact batches, groups by exact tags and observation-scope specification, then splits each group into LLM batches. Groups sharing a write scope serialize; disjoint groups can run in parallel. These are processing batch limits, not a requirement to accumulate N facts before starting. [source hindsight_api/engine/consolidation/consolidator.py:1602] [source hindsight_api/engine/consolidation/consolidator.py:1620] [source hindsight_api/engine/consolidation/consolidator.py:1630] [source hindsight_api/engine/consolidation/consolidator.py:1953] |
| Round continuation | Reaching the per-round fact limit enqueues another consolidation through the same submission chain. The current operation can complete with a successor pending. Enqueue failure propagates into retry rather than silently claiming the backlog is complete. [source hindsight_api/engine/consolidation/consolidator.py:2005] |
| Periodic recovery schedule | **A schedule exists:** maintenance runs reconciliation at startup and then every configured interval, default 300 seconds, with a 60-second loop tick. It discovers eligible unscheduled Banks and submits through the same chain, gated by observations and auto-consolidation. This is a recovery sweep, not a daily or inactivity-based consolidation schedule. [source hindsight_api/engine/maintenance.py:21] [source hindsight_api/engine/maintenance.py:57] [source hindsight_api/engine/maintenance.py:163] [source hindsight_api/engine/maintenance.py:338] [source hindsight_api/engine/maintenance.py:380] |
| Delete / update maintenance | Auto-consolidation also follows mutations that make observations stale; document deletion explicitly resubmits when it invalidated observations. This matters when evaluating a timing change beyond retain. [source hindsight-docs/versioned_docs/version-0.9/developer/api/memory-banks.mdx:190] [source hindsight_api/engine/memory_engine.py:7553] |
| Explicit manual trigger | `POST /v1/default/banks/{bank_id}/consolidate` enqueues a full or scoped operation and returns its ID and deduplication result. [source hindsight_api/api/http.py:7084] |
| Transient-failure delay | Consolidation retries use capped exponential backoff: 5, 10, 20, ... seconds, capped at 1,800 seconds. Another pending consolidation can replace the failed attempt's retry responsibility. This is outage recovery, not ordinary debounce. [source hindsight_api/engine/memory_engine.py:283] [source hindsight_api/engine/memory_engine.py:3146] |

### Q2. Persistence and crash/restart recovery

Native persists **queue ownership** in `async_operations`: operation ID, Bank, type, payload, status, worker claim and retry state. Payload and pending-row insertion are atomic, closing the crash window that would otherwise leave an unclaimable null-payload job. Full-Bank conditional admission is serialized before checking and inserting. [source hindsight_api/engine/memory_engine.py:17524] [source hindsight_api/engine/memory_engine.py:17554] [source hindsight_api/engine/memory_engine.py:17619]

Native persists **completed source work** in each fact's `consolidated_at` and **terminal model failure** in `consolidation_failed_at`. Candidate retrieval selects only unmarked world/experience facts, oldest first. It does not reconstruct progress from the model heartbeat or replay every historical fact. [source hindsight_api/engine/consolidation/consolidator.py:1383] [source hindsight_api/engine/consolidation/consolidator.py:1404] [source hindsight_api/engine/memories/pg/reads.py:355]

| Interruption / failure | Recovery and actual granularity |
| --- | --- |
| Pending job, before execution | The durable payload remains available for the ordinary worker claim. Jobs for a Bank already processing consolidation are excluded from a new consolidation claim. [source hindsight_api/engine/memory_engine.py:17619] [source hindsight_api/engine/db/ops_postgresql.py:1381] |
| Worker crashes while processing | On startup, the **same worker ID** reclaims its processing rows: under the recovery budget they return to pending and consume a retry; at/over the budget they become failed. Default worker identity is hostname. This is not a promise of arbitrary different-worker takeover. [source hindsight_api/worker/poller.py:912] [source hindsight_api/worker/poller.py:994] [source hindsight_api/worker/main.py:183] |
| Source markers already committed | A rerun skips those source facts. Marker/revision/journal publication is atomic in the Taki PostgreSQL path. **Source identity is the durable granularity; marker commit happens for the processed LLM batch**, including any adaptive sub-batches, not for the entire Bank or 100-fact round. [source hindsight_api/engine/consolidation/consolidator.py:1751] [source hindsight_api/engine/consolidation/consolidator.py:1769] [source hindsight_api/engine/consolidation/consolidator.py:1776] [source hindsight_api/engine/memories/pg/reads.py:372] |
| Crash during an unmarked LLM batch | Its still-unmarked facts are eligible again. Already committed observation actions remain, and later recall/dedup considers existing observations. PostgreSQL observation actions have their own short transactions before the final source-marker transaction; the SQL store's cross-store transaction handle is a no-op. Therefore **a completed remote LLM call or an individual action is not an exactly-once assessment checkpoint**: the interrupted batch can be reassessed, and action-level dedup is not proof of identical model output. [source hindsight_api/engine/consolidation/consolidator.py:1689] [source hindsight_api/engine/consolidation/consolidator.py:2833] [source hindsight_api/engine/consolidation/consolidator.py:3527] [source hindsight_api/engine/consolidation/consolidator.py:1769] [source hindsight_api/engine/memories/base.py:435] [inference] |
| Individual fact repeatedly fails the model | Native retries/splits a failing batch down to singleton facts, then marks singleton failures. Failed facts are excluded from normal candidate retrieval. The explicit `/consolidation/recover` route resets failed markers for a later consolidation; they are not silently reclassified as success or endlessly retried as ordinary pending facts. [source hindsight_api/engine/consolidation/consolidator.py:1669] [source hindsight_api/engine/consolidation/consolidator.py:1751] [source hindsight_api/engine/memories/pg/reads.py:374] [source hindsight_api/api/http.py:6917] |
| Transient infrastructure failure | The operation retries with specialized capped exponential backoff, unless another pending consolidation already owns the same remaining work. Already marked sources stay skipped. Deterministic failures are terminal instead. [source hindsight_api/engine/memory_engine.py:3116] [source hindsight_api/engine/memory_engine.py:3146] [source hindsight_api/engine/memory_engine.py:3163] [source hindsight_api/engine/memories/pg/reads.py:372] |
| Lost successor admission / terminal job with eligible backlog | Round requeue failures propagate into retry. The periodic reconciliation also finds eligible unscheduled Banks with no in-flight consolidation, when auto-consolidation remains enabled. [source hindsight_api/engine/consolidation/consolidator.py:2005] [source hindsight_api/engine/maintenance.py:8] [source hindsight_api/engine/maintenance.py:380] |

The job writes best-effort phase/batch progress into `async_operations.result_metadata.progress`, with processed/total/detail and a timestamp. These counters help status polling but are **not the resume checkpoint**; they restart for a new execution while the source markers preserve factual progress. Completion is persisted separately with a terminal operation state. [source hindsight_api/engine/memory_engine.py:3441] [source hindsight_api/engine/consolidation/consolidator.py:1550] [source hindsight_api/engine/consolidation/consolidator.py:1905] [source hindsight_api/engine/memory_engine.py:3716] [inference]

Do not transfer its deferred-visibility guarantee to SQL observation actions. Ordinary Taki finite-maintenance admission and late-write fences remain part of the fork's supported chain. ### Q3. Config-only deferral/batching and recall cost

**Yes for disabling automatic admission and tuning existing processing batches; no for a self-running daily/debounced consolidation schedule through config alone.** Native's documented control is `enable_auto_consolidation=false` / `HINDSIGHT_API_ENABLE_AUTO_CONSOLIDATION=false`, while leaving observations enabled, then explicitly calling the existing consolidate endpoint when the desired ingest batch is ready. This needs no Native algorithm change, but the caller still owns the trigger. [source hindsight-docs/versioned_docs/version-0.9/developer/api/memory-banks.mdx:190] [source hindsight_api/api/http.py:7084] [inference]

- Config-only batching uses `HINDSIGHT_API_CONSOLIDATION_BATCH_SIZE`, `..._LLM_BATCH_SIZE`, `..._LLM_PARALLELISM`, and `..._MAX_MEMORIES_PER_ROUND` as specified above. Increasing them does not delay admission until a threshold. Native already batches by default. [source hindsight_api/config.py:1192] [source hindsight_api/engine/consolidation/consolidator.py:1602] [source hindsight_api/engine/consolidation/consolidator.py:1630]
- Setting reconcile to `86400` while auto-consolidation stays true **does not defer retain-triggered jobs**. Setting auto-consolidation false also disables that Bank's reconcile submission, so the two knobs cannot be combined into a config-only daily scheduler. Reconciliation runs immediately after restart before its later intervals; it is not a stable wall-clock 03:00 anchor. [source hindsight_api/engine/memory_engine.py:5063] [source hindsight_api/engine/maintenance.py:163] [source hindsight_api/engine/maintenance.py:380]
- Switching auto-consolidation off does **not cancel previously queued/processing jobs or their round continuation**: execution checks the observations gate, and round continuation submits explicitly. A clean timing transition therefore must account for accepted work rather than assuming the toggle drains the Bank. [source hindsight_api/engine/consolidation/consolidator.py:1509] [source hindsight_api/engine/consolidation/consolidator.py:2018] [inference]
- `HINDSIGHT_API_ENABLE_OBSERVATIONS=false` disables the feature, including manual consolidation. Disabling workers or making their polling interval very large delays unrelated async retain/import/refresh work too. These are not suitable consolidation-only scheduling controls. [source hindsight-docs/versioned_docs/version-0.9/developer/api/memory-banks.mdx:186] [source hindsight_api/engine/memory_engine.py:3047] [source hindsight_api/worker/poller.py:178] [inference]

**Source/documented recall cost:** raw world/experience facts can be recalled without consolidation. New or refined observations lag while consolidation is deferred; an observations-only recall can therefore miss recent retained evidence. Native's recall documentation explicitly distinguishes raw-fact coverage from observation lag and explains that mixed-type recall can include both. Consolidation-driven mental-model refresh is also postponed until the final consolidation round. Independently cron-scheduled models remain a separate refresh chain. [source hindsight-docs/versioned_docs/version-0.9/developer/api/recall.mdx:85] [source hindsight_api/engine/consolidation/consolidator.py:2058] [source hindsight_api/engine/maintenance.py:14]

Taki passes the requested fact types to Native recall and can install exact neutral policy for newly hydrated candidates without waiting for the curator. Thus **D108 review deferral delays policy/Block enrichment; Native consolidation deferral separately delays observation synthesis**. Raw recall is not a promise that observation-only requests retain equal coverage or that reasoning quality is unchanged. The magnitude of real-model quality loss at 24 hours is UNKNOWN; no such comparison was run. [source packages/core/src/memory/hindsight/hindsight-memory-recall.ts:24] [source packages/core/src/memory/hindsight/hindsight-memory-recall.ts:29] [source .trellis/spec/backend/hindsight-application-runtime.md:130] [source hindsight-docs/versioned_docs/version-0.9/developer/api/recall.mdx:89] [inference]
