## Implementation decision after the diagnostic

The pre-change diagnostic proves a remaining dependency on subsequent binding; it does not
prove redundant immutable downloads or quantify the post-wave-1 latency. The
leader subsequently narrowed the proposed stop boundary to the end of an entire
`applicationChanges` page. This preserves the existing event and page checks.

### Approved production delta

The leader inspected the diagnostic and approved this narrow page-boundary target
on 2026-11-11 within the owner's wave-2b authorization. Implementation and actual
validation results follow below; the pre-change observations remain the baseline,
not post-change acceptance.

1. Pass the already accepted command's authority epoch, namespace and receipt
   checkpoint into the existing bounded Bank synchronization path. Keep original
   command IDs, queued Bank ownership, lease, cancellation and deadline handling.
   Capture/check the target identity once at the normal admission boundary; it is
   a stopping target, not publication evidence.
2. After the existing incremental loop has applied every complete event in its
   current page and passed its existing `to_checkpoint`/`has_more` checks, compare
   the local native/state cursor pair with the target. If covered, return before
   fetching another page. Target mode skips `bindPasses`; an unmet goal remains
   unconfirmed rather than attempting unrelated binding. Do not branch inside an event or
   bypass the current page's remaining checks. A full-snapshot reset keeps its
   existing complete proof and rollback/generation rules before this same decision.
3. Retain the curator's single terminal `writer.applied` check and only then
   complete the saved result. For a recovered job already marked completed before
   `writer.run`, an early exact `writer.applied` check can avoid a needless pull;
   do not add that read to every newly published item.

### Focused failure cases for the production decision

- The target follows earlier events: apply every intervening event; a target in
  the middle of a page also requires the rest of that page before returning.
  Hold the next page and binding to show neither is required for this completion.
- The rest of the current page is invalid: retain existing error/partial-event
  publication behavior; never call the work completed by skipping page validation.
- Target cursor coverage without its exact artifact history is insufficient:
  retain the existing `writer.applied` refusal and saved work.
- Authority/namespace changes, rollback, missing target, cancellation or lost lease
  do not complete the item or mint a replacement command. Reuse existing guards;
  extend tests only at newly introduced target propagation/return boundaries.
- Reset/retry preserves the same target and fixed budget; an old target must never
  be reinterpreted in a replacement Bank generation. A recovered already-applied
  job needs no remote pull; a completed receipt alone still requires convergence.

Trade-off: a complete page can contain unrelated later events (the current request
limit is 128 manifests), so this deliberately permits bounded overpull rather than
introducing partial-page semantics. A large event or an earlier queued Bank owner
can still delay convergence. Binding remains on ordinary maintenance/synchronization;
this mode does not promise a new immediate wake or full Bank enrichment. Real-provider
timing, concurrent usability and cache-miss attribution remain unmeasured.

## Implemented behavior and work cost

- `hindsight-policy-curator-context.ts` and `hindsight-replica-sync-runner.ts`
  carry one optional internal goal using the existing Shared namespace/checkpoint
  types. No new wire schema, stored cursor, cache, observer, queue or stop framework
  was introduced.
- `hindsight-policy-curator-publication.ts` supplies the original accepted job's
  epoch, namespace and checkpoint. Newly dispatched work performs one terminal
  exact `writer.applied` proof after refresh. Recovery first checks only jobs that
  were already completed: exact local history then permits synchronous journal
  completion without re-entering the writer queue or making a remote request.
  A completed receipt without local history still follows normal target catch-up
  and the terminal exact proof; no command or operation identity is replaced.
- `hindsight-memory-subsystem.ts` forwards the third refresh argument to the same
  service. `hindsight-runtime-bank-service.ts` retains that goal across its Bank
  queue, original lease/deadline and existing reset spread. No-target foreground,
  scheduled and recovery callers keep their original behavior.
- `hindsight-application-sync-runner.ts` checks target epoch/lineage and namespace
  once after normal admission, reusing the checkpoint already read there. A reset
  requests the accepted namespace; it cannot discover and reinterpret a replacement
  generation. Existing full snapshot, rollback, body/event/page and publication
  guards still own proof. Page-end comparison is only two integer comparisons;
  no per-event receipt lookup, artifact scan, hash or added checkpoint read occurs.

The deterministic target case commits an intervening event, the policy event and
the remainder of its page. It performs one changes request, leaves a fourth event
on the next page and makes zero binding calls. New publication invokes
`writer.applied` once. Already-applied recovery invokes that exact proof once and
performs zero writer dispatches or refreshes. These are eliminated dependencies
and request/work counts, not measured production latency improvements.

The remaining page can include up to the current 128-manifest request limit; a
large event and an earlier serialized Bank owner can still delay completion.
Unrelated binding is deferred to existing ordinary synchronization/maintenance;
there is no new immediate wake. Policy completion is not full Bank convergence.
Recovery of an already completed but unapplied job pays an unsuccessful early
exact proof before catch-up and the required successful terminal proof.
