- Query: Define concrete admission, autonomous-context, tool/outcome, held-delivery and Monitor adaptations on the existing framework, including lifecycle and compatibility hazards.
- Scope: internal; current T4 source, existing specs and the parent Heartbeat research. Signal/Pattern/Intention/Presence domain design and Memory integration inventory remain parent/peer responsibilities.

## Findings

The existing framework is sufficient to begin staged implementation. The necessary shared extensions are part of this development task, not a prerequisite replacement runtime. They must nevertheless land before the product paths that depend on them: atomic background admission, a real autonomous context contract, structural decisions, delivery continuations, factual delivery producers and versioned business-event readers. Merely selecting `initiator=heartbeat` does not implement these contracts.

“Heartbeat” as the broad product family does not erase runtime distinctions: Scheduled Class A, autonomous Class B and maintenance retain their respective policy, model-routing and recovery behavior. This report recommends one existing Agent loop and one execution ledger throughout.

### 1. Common admission, Character priority and bounded deferral

1. Add an atomic priority/reservation extension to the existing `TurnQueue`. Primary work registers its intent before asynchronous admission/snapshot capture and transfers that reservation to the pump; failure, disconnect and cancellation release it. Preserve FIFO within a priority class and concurrency across Characters. A background `tryAcquire` must see both holders and queued/reserved primary work.
2. A Class B candidate first passes domain eligibility, then obtains the background lane reservation, revalidates freshness/current policy, and only then calls `RunService.admit`. If the lane is busy, persist a bounded policy deferral without creating a Run or model request. Do not perform an unlocked “is idle” check followed by a separate acquire.
3. Keep at most one pending Class B candidate and one held output per Character, under the domain's coalescing/latest-wins contract. Re-evaluate at a real release/breakpoint or bounded timer; do not accumulate scheduler ticks or reuse expired Intentions. Use an idempotency key for the accepted opportunity; reuse RunService admission rather than another execution queue/store.
4. User work wins at admission and delivery. **No mid-tool-chain preemption**: the existing research expressly says to finish safely and discard stale output (`.trellis/workspace/pleia/t4-heartbeat-engine.md:611-612`). `busyMaxWait` is a skip/expiry bound, never a deadline that authorizes interruption of primary work. Preserve the current 90-second starting bound; a new primary arrival invalidates or revalidates pending output against its captured context.
5. Scheduled Class A can share queue mechanics while retaining expected-work/catch-up policy. Maintenance keeps its existing Utility/compaction coordination. Do not impose Class B expiry/counters on either merely because the broad product terminology groups them together.

Ownership: the shared admission slice owns `turn-queue.ts`, `chat-send.ts`, the provider adapters and Run admission integration. The domain slice supplies `EligibleOpportunity`, validity and coalescing facts; it does not own a second Character mutex.

### 2. Thin autonomous context and captured source manifest

- Add an explicit captured autonomous-input contract to `TurnContext` / `RunExecutionContext`. A new initiative Run must select this profile deliberately; absence must fail closed for that provider rather than silently falling back to full relationship replay. Keep primary and existing compatibility callers unchanged until explicitly migrated.
- Capture the bounded model-facing context once per accepted Run and reuse it across the existing overflow Attempt retry. It comprises the domain-approved fragments and sanitized control input; it is not a synthesized persisted user turn. Continue through the same `ToolLoopAgent`, `prepareOutgoingRequest`, model Effect middleware and Main Model. Do not instantiate a second Agent or select the Utility Slot for initiative.
- Extend the durable snapshot with a **versioned, bounded source manifest**: context profile, source categories/references, source revision/generation, capture/expiry times, trust classification, selected policy version, primary-admission/history fence, authority references and measured/estimated token-accounting quality. These are provenance facts, not raw Persona, prompt, Memory, sensor or tool payloads. Display projections use useful labels and omit opaque internal identity.
- Keep protected prompt fragments process-local. Store only the final user-facing output in a confined delivery record when needed for held delivery. A restart does not reconstruct the model request by replaying the entire conversation or silently reacquire new authority for an old decision.
- The current reducer measures the supplied outgoing request (`packages/core/src/agents/request-preparation.ts:53-68`). Feed it the thin request and its matching measurement; do not attach primary Replay measurements to unrelated autonomous fragments. Preserve `.trellis/spec/backend/compaction-harness.md:35-37`: non-primary receives its own reduction/Run telemetry but never replaces the relationship pressure snapshot or advances conversational auto-memory/flush watermarks.

Ownership: context/runtime slice owns `harness-schema.ts`, `run-snapshot-capture.ts`, `chat-agent.ts`, `request-preparation.ts` and a focused new autonomous-context adapter. Provider-neutral Memory fragment production stays with the parent integration slice; no Local-repo or Markdown bypass is recommended here.

### 3. Run-scoped tool policy and structural terminal decisions

- Add a captured **runtime tool restriction**, independent of permission authority: initiative v1 advertises only its approved Core reads, relevant Skill reads and the structural response control. Apply the restriction when constructing schemas and again before dispatch. Existing governance remains stricter-only and authoritative; the restriction never grants permission. Do not trust a model-supplied initiator/class or identify safe tools through name substrings.
- The generic non-primary bag is too broad: `packages/core/src/main.ts:306`, `:389` supplies ordinary static Core tools including `write_file`, while ChatAgent also composes Memory/avatar/extensions. Do not confuse no operator socket with the v1 no-exec/no-external-effect/no-new-sensor boundary. Preserve unattended `APPROVAL_REQUIRED` with no ambient prompt (`permission-authorization.md:260-261`; `governed-tool.test.ts:201`).
- Implement `heartbeat_respond` as a trusted Run-scoped control tool with a strict `silent | express | speak` union. Silent carries no utterance; express carries only bounded presentation intent; speak requires the complete bounded user-facing text and may carry optional presentation intent. Core attaches identities/provenance. Runtime policy reasons come from Core facts, not a model-generated explanation masquerading as evidence.
- The tool stages a decision; it does **not** publish text, execute an avatar command or settle the whole Run. A per-Run/Attempt collector accepts one valid decision, treats an exact duplicate idempotently and rejects a conflicting or stale call. Commit the decision only after the stream's authoritative settlement check succeeds and cancellation has been checked.
- Stop the AI SDK loop on **accepted structural decision**, not merely seeing that tool name in a failed/invalid tool call. Keep the step cap as a failure bound. Missing/invalid terminal output fails the Run with a closed diagnostic; it is not automatic silence or success. Free-form model deltas remain private and are not a substitute for the structural `speak` payload.
- Existing `presentationTailStop` requires prior text (`packages/core/src/avatar/presentation-stop.ts:23`) and cannot terminate structural silence. Do not mutate it globally. Explicitly integrate the terminal control with the fixed Core binding/registration path: `core-tool-governance-adapter.ts:101-109` deliberately closes unknown executable tools. Do not add a permissive general bypass.
- For initiative reasoning, exclude the immediate-execution avatar tools or adapt them to stage the same output intent. The recommended v1 path is the terminal intent only. The delivery phase later invokes the existing governed avatar execution with the original active Run/Attempt. Preserve dynamic vocabulary/costume validation; do not publish an expression during reasoning and then claim a silent outcome.

### 4. Decision, held delivery and Run termination: explicit lifecycle contract

`heartbeat_respond` terminates model reasoning. Run termination depends on whether executable work remains. A delivery record is subordinate business state linked to the existing Run, not another Run/Attempt ledger.

| Decision / phase | Run/Attempt and Character slot | Permitted next work |
| --- | --- | --- |
| Silent | Commit the decision and settle the Run; release the slot. | Append decision evidence only; no Timeline row, avatar dispatch or empty conversation turn. |
| Speak, text only | Atomically stage the immutable output and complete execution; release the slot. | Ordinary Timeline delivery is a post-execution projection, gated by current delivery policy. It does not call tools or reopen the Run. |
| Express, or speak with an executable expression | While the original Attempt remains active, stage a typed delivery continuation. If blocked, CAS Run `running -> waiting` with reason `delivery`, then release the slot. | No Effect/Host/tool dispatch while waiting. The model will not run again. |
| Held executable presentation becomes eligible | Acquire the shared background slot; verify continuation version, active Attempt, deadline/TTL, primary fence, exact Host/costume/source generations and current governance. CAS `waiting -> running` for the **same Attempt**. | Invoke only the staged governed presentation operation, settle its real Effects, then settle the Run and release the slot. Text can then use the ordinary projection. |
| Held work expires, is superseded, loses authority or is cancelled before dispatch | Settle the continuation/Run truthfully and release retained bindings/reservations. | No model retry, no replacement Host and no late avatar execution. Pure-text projection may expire without changing the already terminal Run. |
| Renderer/transport evidence arrives later | Keep the original Run state unchanged, including a terminal pure-text Run. | Append bounded delivery evidence under the same `runId`; do not invoke another effect. |

**Required shared extension:** `RunService`/`RunRepo` need guarded hold/resume methods for an explicit delivery continuation. Current `start` rejects non-queued state (`run-repo.ts:123-124`), and `guardDispatch` accepts only running state (`:208-223`). Do not weaken that guard or reuse `start`/`retry` as an undocumented resume. Hold only after the reasoning effects are settled; keep the Attempt non-terminal. A latest-wins replacement may retire a waiting, undispatched continuation, not cancel an executing tool chain.

**Recovery hazard:** `recovery-coordinator.ts:70-76` currently treats a last completed model Effect as grounds to complete the whole non-queued Run. Add continuation-aware classification before that repair. A staged presentation is incomplete work even when all model Effects are terminal. On restart, revalidate a known-undispatched continuation only when its original binding can be proved current; otherwise expire/refuse it. A dispatched or uncertain expression remains `outcome_unknown`/reconciliation-required and is never republished automatically. Tests must cover all crash cuts. No background model rerun and no new “delivery Run” are needed.

**Text versus presentation truth:** ordinary assistant persistence exists (`conversation-store.ts:145`) and does not require a live tool Effect. Its current hook publishes immediately after append (`:119-122`), so add a transaction-aware seam that commits the Timeline row, delivery linkage and budget transition before any outward publication; reuse `timeline-repo.ts:117-131` and the existing subscription path. This must not manufacture a foreground `ChatActivity` turn. Only the structural full utterance enters Timeline; silent/express-only output never does. Do not mislabel a model Run's `completed` as sent, shown or read.

**Class B delivered-utterance accounting, separate from model count and ACKs:**

1. Give each logical spoken utterance one durable delivery identity. Atomically reserve its Class B budget/gap capacity and outbox state so concurrent dispatchers, retries and multiple frontends cannot consume or publish it twice. Keep the ratified limits (2/hour, 8/day, 10-minute gap) in the configured policy; Class A does not consume them.
2. If policy rejection/cancellation/expiry is known to occur **before any publish starts**, release the reservation and create no “delivered” fact. At the dispatch boundary, atomically commit the budget decision and the single canonical Timeline row/link, then fan out. Never release the reservation first and then publish.
3. Once fan-out may have occurred, an uncertain result consumes at most one slot conservatively; do not refund and create a fresh logical utterance. The budget charge is an upper-bound control fact, not a fabricated confirmed-send count. Retries cannot create another Timeline row or restart the gap under a new identity.
4. Emit `sent` only from a real transport outcome. Current void `notify`/`publish` and `socket.send` invocation alone do not provide that producer. Add an observable result seam to the existing sender; distinguish no eligible target, refusal before dispatch, confirmed transport acceptance and uncertain fan-out. Do not infer it from subscriber count, Pino or `ok:true`.
5. Emit `presented` only from an authenticated, current-generation, message-specific frontend observation after actual rendering under the existing presentation gate. Core validates identity, Character, surface, freshness and duplicate/multi-client reports. It is not proof of reading. ACK timing never grants additional delivery budget, and ignore-backoff consumes only the separately validated presence/presentation evidence specified by the domain design.

Before publication, busy/quiet/privacy/source/expiry checks run again from already available Core facts without a model call. Pure-text post-execution revalidation cannot acquire new observations or dispatch a tool/Host effect. After publication, expiry suppresses stale live presentation/reconnect replay; it does not erase canonical relationship history. Expression and text delivery are independently evidenced: an optional expression failure cannot be reported as shown merely because its text was committed. An unresolved executable effect retains its truthful Run outcome even if text delivery succeeded.

### 6. Pattern-authoring Skill: standard package/import, not developer skills

- Current runtime entry is `packages/core/src/skills/skill-boot.ts:22-30`: the durable store is `<dataDir>/skill-packages`; `<dataDir>/skills` is only a one-time legacy seed when the repository is empty. This boot code has no bundled product-Skill installer. Do not put the Companion's runtime Skill under `.agents/skills`, rely on the legacy seed for upgrades, or overwrite a published package directory.
- Smallest explicit distribution recommendation: add a standard source package at `packages/core/resources/skills/companion-pattern-authoring/SKILL.md` with matching metadata `name: companion-pattern-authoring` and optional `references/`; package it as a normal ZIP asset for delivery. This proposed resource path/packaging step does not exist yet. Installation is an explicit setup/import step through the existing operator `skill.import`, not a new catalog or permission channel.
- The actual import accepts **bytes**, not a Core filesystem path: `packages/shared/src/skill-lifecycle-schema.ts:59-63` defines directory `{ files: [{ path, contentBase64 }] }` or ZIP `{ fileName, archiveBase64 }`. `packages/core/src/server/methods/skill-methods.ts:16` routes that operator method to the existing lifecycle service. Any later setup automation must construct the same payload and use the same service; it must not bypass scan, immutable publication, enable state, catalog generation or leases.
- `packages/core/src/skills/skill-lifecycle-service.ts:75-86` refuses an existing same-name package and replaces only an explicit `replacePackageId` plus `expectedConfigRevision`. A shipped update therefore cannot silently replace or re-enable a user's Skill. The installed Skill teaches use of the typed Pattern candidate/revision API; it cannot directly write Pattern storage, Persona, runtime code or grant Capability permission.
- Reuse `skills/skill-boot.test.ts:25` (durable truth wins after seed/reopen), `skills/skill-lifecycle-service.test.ts:19` (replacement revision required), and the source/loader/resource tests. Add one fresh-profile package-import -> metadata discovery -> `load_skill` -> Pattern candidate flow, plus same-name user-package and disabled/replaced-package preservation. This setup/install step is part of the first authoring delivery's acceptance, not an assumed installed asset.

These remain planned checks, not executed results.
