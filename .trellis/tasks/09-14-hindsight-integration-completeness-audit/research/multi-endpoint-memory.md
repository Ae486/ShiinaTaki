# Research: Memory-related multi-client and remote-Core usability

- Query: What currently works when Home, Pet and Chat share one Core, when a desktop should use a remote Core, and when independent Cores target one Hindsight deployment? Who owns memory, configuration, credentials and durable operations, and what remains unconnected or unverified?
- Scope: Internal source and accepted-design audit in `H:/TakiAgent`; narrow native admission evidence supplied by the companion native/setup workstream from `H:/hindsight`.
- Date: 2026-09-14
- Task: `.trellis/tasks/09-14-hindsight-integration-completeness-audit`.
- Execution boundary: Source/document reads and this report only. No tests, services, model calls, original user databases, credentials, Git operations, task-pointer changes, or other-worktree access. Current working-tree source outranks historical task status and the semantic index.

## Findings

The current desktop has three independent operator connections to the **same fixed local Core**. Core connection membership, per-Character chat serialization, and subscription fan-out support multiple clients of that Core. Reconnection replaces clients and restores reads/subscriptions without replaying mutations. This is implemented substrate, with outstanding owner-observed acceptance.

A remote Hindsight endpoint is already a separate Core configuration concept. It does **not** select a remote Core for the desktop. Desktop operator transport, the release Shell, and packaged CSP remain bound to loopback. Remote-Core selection belongs to the existing D23/#29 split-deployment work; this audit does not add it to B7.

Core-owned Pending/application journals and recovery are real, but they do not provide the B7 operator experience by themselves. Home currently consumes maintenance counters and `memory.tidy`; it has no Hindsight operation observer that another window can reopen. Core already exposes some setup and cutover status RPCs, so the missing work is not correctly described as “no persisted state anywhere.”

Independent Cores sharing a Hindsight service or Bank are a different topology. Deterministic Bank names and the native application namespace do not encode a Core/user/profile identity. Existing epoch, namespace, revision and import guards remain mandatory; their presence is not proof of supported active-active operation, tenant isolation, or an observed data leak.

### Independent Cores and a shared Hindsight service

The supported single-Core multi-client case must not be conflated with either of these cases:

1. **Independent Cores, intended distinct Banks on one service.** Taki's deterministic Global ID and same-Character ID do not accept a Core/profile/user salt or an operator-selected external Bank mapping in the inspected setup path. A generic service's ability to host multiple Banks is not proof that Taki has delivered isolated per-Core tenancy. This audit found no executable end-to-end acceptance for that topology and did not run it.
2. **Independent Cores, the same existing Bank.** They would still have independent local epochs, replicas, leases, outboxes, configuration and secret catalogs. The current namespace only binds provider lineage/Bank generation/application ID. It must not be treated as active-active coordination or as authorization to merge those Cores.

There are meaningful refusal boundaries. The native/setup workstream inspected `H:/hindsight/hindsight-api-slim/hindsight_api/engine/transfer/current_state_admission.py:132-185`: the locked target view must match the target Bank plus preserved/superseded objects; pending native work or unexpected objects produces `target_conflict`, and revision/hash drift produces `ownership_drift`. `H:/hindsight/hindsight-api-slim/hindsight_api/engine/transfer/current_state_schema.py:252-262` limits preserve entries and requires supersede ownership evidence; `:275-285` binds provider lineage/Bank generation. `H:/hindsight/hindsight-api-slim/hindsight_api/engine/application_state/store.py:136-164` validates that incarnation and Bank existence/deletion state. These guards must remain intact.

Taki's own first-promotion path also requires an active `initial-local` predecessor and completed B2 source receipt: `packages/core/src/db/hindsight-authority-repo.ts:79-96`, `packages/core/src/db/hindsight-cutover-run-repo.ts:111-116`. Those checks prove local migration preconditions, **not** cross-Core isolation. A second-Core attempt may be refused by existing admission gates; this report does not claim a bypass, observed corruption, or a data leak.

The accepted same-profile Local/Hindsight re-entry rule remains unchanged: reuse verified common state, identity mappings and later changes. Cross-Core limitations must not be used to demand new physical Banks, a different Hindsight service, or full retransmission for every ordinary provider switch.
