## Findings

### F1 (low-medium, fixed): shutdown could restart the replica scheduler after the memory runtime stopped it

Where:

- `packages/core/src/main.ts:568`;
- `packages/core/src/memory/hindsight-backup/hindsight-backup-service.ts:106`.

Problem:

- `hindsightBackup.stop()` only aborted the capture's controller, and nothing waited for it.
- A capture's `finally` releases the fence and calls `scheduler.start()` if the scheduler was running.
- A capture inside `Database.backupTo` does not see the abort until the copy ends. Its release could therefore land after `memoryRuntime.stop()` had stopped the scheduler for good, which starts a timer on a runtime that is shutting down.

Fix:

- `stop()` now returns a promise. It aborts every capture, then waits for all of them to settle; `active` keeps each capture's promise.
- `main.ts` joins it with the other memory stops before `memoryRuntime.stop()`.

Test: `hindsight-backup-service.test.ts` "stop() during the Core copy resolves only after the capture released its pause and restarted the scheduler". It holds `backupTo` open, calls `stop()`, and checks that when `stop()` resolves the scheduler has been restarted once and the fence is writable. The capture itself settles `HINDSIGHT_BACKUP_NATIVE_FAILED`.

### F2 (medium, fixed; known item 1): Home depended on the 20-row operations window and could not re-verify a failed-verify backup

Before this fix:

- Home found a route-b staged capture by searching `operations.recent` (last 20 rows). After 20 other operations the staged capture vanished from Home, and the operator could no longer import its ZIP.
- The 校验备份 action targeted only `lastVerified`. A backup whose `verify` failed has `verifiedAt: null`, so it was never offered again.

Fix, by layer:

- **Shared** (`packages/shared/src/hindsight-backup-schema.ts:185-196`). `HindsightBackupStatusSection` gains two fields:
  - `latest`: the newest sealed backup whatever its verification, as `{backupId, createdAt, verifiedAt|null}`;
  - `staged`: the current epoch's route-b captures still waiting for their ZIP, newest first, at most 16.

  Two rules are added: a section with `lastVerified` must have `latest`, and a staged id appears once. No `index.ts` change was needed, because the section schema was already exported.
- **Core store** (`hindsight-backup-store.ts:267`). New `listStagedSync()`:
  - it lists `<uuid>.staged` dirs whose `core-identity.json` parses and names the dir itself;
  - partial dirs, foreign names and unreadable identities are skipped.

  `listManifests` and `readManifest` now share the same `listNames` and `readJsonSync` helpers.
- **Core service** (`hindsight-backup-service.ts:113`). New `inventory()` returns last verified, newest sealed and staged. It uses the same cache as `lastVerified()`, which capture, admit and verify invalidate.
- **Core status** (`hindsight-backup-status.ts:47`). It keeps only staged captures of the current epoch, because older epochs are not admissible. It caps the list at 16. The emergency seal passes no inventory, so there `latest` falls back to `lastVerified`.
- **Core authority status** (`memory-authority-status.ts:111`). It reads `inventory()`. A read failure still gives a null section.
- **Desktop** (`memory-hindsight-backup-state.ts:99,107,160,167`):
  - the staged capture comes from `section.backup.staged[0]`, with the epoch from `status.authority.epochId`;
  - 校验备份 targets `latest`;
  - a new row 最新备份 = `<createdAt>（未通过校验）` appears when `latest.verifiedAt` is null;
  - the id of `latest` goes to diagnostics when it differs from the verified one;
  - the primary rows still show no ids or codes.

Tests:

- Shared: a failed-verify section; refused sections (verified without latest, duplicate staged id, bad staged id).
- Core:
  - store/service: the staged listing skips a staged dir without identity, a partial dir and a non-uuid name (`hindsight-backup-admit.test.ts`);
  - status: latest unverified; epoch filter;
  - journey (`memory-operation-kind-backup-admit.test.ts`): after the route-b capture the status lists it as staged; after admit, staged is empty and `latest` is the admitted backup.
- Desktop:
  - staged is found with no operation rows at all;
  - a completed capture row without a staged entry offers nothing;
  - a failed-verify newest backup, both beside a verified one and without one, shows the 最新备份 row, and verify targets it.

### F3 (info; known item 2): native `zipfile` on the API event loop

The W5 note says the native backup compresses on the event loop. That is outdated. In `hindsight_api/admin/cli.py:352-354`, both `zf.writestr` of each table and the per-entry hash already run in `asyncio.to_thread`, and `api/taki_backup.py:198,216` hashes the finished ZIP in a thread.

What still blocks the loop during a capture:

- `fh.flush()` and `os.fsync()` in `api/taki_backup.py:196-197`. This is one fsync of the whole ZIP; on a slow disk it can take seconds.
- The final `zf.writestr("manifest.json", ...)` and the ZIP close (`cli.py:369`). These are small.
- `buffer.getvalue()` (`cli.py:350`). It is cheap in time, but it keeps each table's COPY output twice in memory. Peak memory is about 2x the largest table.
- `typer.echo` progress lines (`cli.py:332,365`), which write to the API's stdout.

Recommendation:

- Move `flush` + `fsync` into `asyncio.to_thread` the next time TAKI-HS-013 is touched.
- Optionally, skip the progress echo when called from the endpoint.
- Log the memory buffering as a deferred item if large Banks are expected.

None of this blocks Stage 3 at owner scale. The Core side is bounded anyway, because the native call is raced against a 600 s deadline (`hindsight-backup-service.ts:191-194`).

### F4 (low, leader decision): an explicit full reconciliation on a rolled-back native gives a different code

`hindsight-application-sync-runner.ts:120` sends `kind: "full"` runs straight to `full()`. The rollback check at `:128`, `refuseRollback`, only runs on the incremental path.

On a native instance that was restored to an older point:

- the full run's snapshot is refused by `hindsight-application-replica-publication.ts:131-132` with `HINDSIGHT_APPLICATION_CHECKPOINT_STALE`;
- so the rollback is never absorbed, and R7 holds for its data;
- but the code is not `HINDSIGHT_PROVIDER_ROLLBACK_DETECTED`, and the Bank is not held for the operator.

This was not changed here: it is a policy choice, and the W6 hold ruling covers the incremental path only.

### F5 (low, no change): smaller observations

- A capture interrupted by a restart settles `outcome_unknown` even when its sealed dir exists. W6 ruled this truthful.
- An unreadable manifest or staged identity makes the whole `backup` section null instead of skipping one entry. This happens only on errors other than a missing file, for example a permission error. It is the same behavior as the listing before this check.
- The native request allows up to 1M operation ids, a body of about 515 MB. That is far above owner scale; it is noted only as a limit.
- `scheduler.started()` is read outside the `try` in `paused()`. It is a plain getter, so it cannot leave the fence closed.
- `main.ts` is 592 lines. It was already 591 before this check, far over the 360 line limit. Splitting it is not part of this task.
- No `.trellis/spec` file covers Stage 3 backup yet: store layout, status section, shutdown order, Home block rules. That belongs to the update-spec step.

### Verified with no finding

- **Workspace only.** Core writes only under `<dataDir>/backups/`. Every path comes from the data dir plus a validated uuid, a fixed dir name or a validated inbox file name.
- **Inbox.** Symlinked or non-regular inbox entries are refused.
- **Secrets.** Custody records only whether a credential ref is present, never its value; `hindsight-backup-custody.test.ts` scans the artifact bytes.
- **Listing.** `.partial`, `.staged`, `quarantine`, `incident-*` and `inbox` are never listed as backups.
- **Fence.** The fence is released in `finally` on every path. A quiesce that timed out reopens the fence itself.
- **Verify.** Verify leaves the manifest untouched for host-state codes (route unavailable, native failed) and clears `verifiedAt` only for an invalid artifact.
- **Rollback.** A rollback on the incremental path is refused and held (7bbd9c3, c63f4f7).
- **Errors.** Every failure path settles a closed `MemoryBackupErrorCode`.
- **Agent access.** No agent tool reaches the backup kinds.
- **Shared entry.** Shared `index.ts` uses only named re-exports.
- **Headers and indexes.** Headers and `index.md` lines of every touched file were updated in the same change.
