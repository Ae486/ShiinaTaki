### Smallest decisive cached-image probe

Inspect packaged metadata/layout to determine whether PostgreSQL/initdb/control binaries are bundled, locally cached or obtained later. 3. Establish the intended exact postmaster/initdb/`pg_controldata` paths and version using bounded version-only commands if already present. Record required loader/library availability, UID-1000 traversal and the empty mounted-data seed. If PostgreSQL is embedded/extracted only by first startup and that cannot be established by metadata, record that as unresolved and make offline extraction into **new owned storage** a separately reviewed first-start prerequisite; do not call it a completed read-only probe.
4. Inspect effective HOME and pg0 path selection from the consumed code. Current consumer HOME is `/home/hindsight/.pg0`, so a default `~/.pg0` may nest beneath that mount. A metadata probe cannot prove pg0 does not detach PostgreSQL or that its `stop` waits. Those must be resolved through the bounded actual-process test. No base image export, broad filesystem scan, heavyweight rebuild or new framework is needed.

### Contract gaps to close before the replacement-child implementation

- **Fixed artifact and admission:** independently review the one replacement file and all staged hashes, its image identity and the explicit `c2a-fake-v1` interpretation. Retain independent fake checks, startup UUID binding, dotenv suppression, fixed argv and DEVNULL. No runtime selection/env map or direct Docker credential injection. Build only from cached inputs with no network or dependency changes.
- **Credential containment:** after validating fake inputs, remove fake variables from the environment passed to every DB/pg0 child. Never map a sentinel to the pg0 password, URI, SQL row, metadata or CLI. Use nonsecret fixture-only local DB parameters in the isolated container; no real connection/provider secret is required. The package's default inherited subprocess environment makes this explicit sanitization necessary.
- **Ownership:** the replacement remains the exact `Popen` child, but PostgreSQL is another process. Record its PID, process start identity, PGID/session and executable. Own an explicit fixed database shutdown path and wait for that postmaster and its descendants; do not rely on the transient `pg0 start` helper PID or group membership assumed from Python source. If group/daemon behavior defeats this, stop and use the standalone case; do not patch generic production supervision during this experiment.
- **Shutdown:** close SQL clients, request the pinned database stop, verify the result and postmaster disappearance, then verify PostgreSQL control state `shut down`. Local `Pg0.stop()` silently ignores nonzero exit status, and existing `OwnedChild` can KILL without a separate public failure marker. Neither returned success nor container exit 0 is decisive. Collect bounded actual utility/log evidence, not just a fixture-authored `stopped` flag. Any forced kill/OOM, unresolved postmaster or unknown stop result fails graceful-stop acceptance.
- **Timing and status:** the unchanged consumer allows five seconds for its running marker; database initialization may take longer. Preserve that marker's meaning as validated wrapper liveness and collect SQL readiness separately with a fixed deadline. Never label the marker as DB ready. The child must handle TERM during initialization, and its DB stop must fit inside the existing 30-second group budget. Allow at least 45 seconds for Docker's outer stop, without extending the 90-second admission grant or claiming forced cleanup is graceful.
- **Evidence and resources:** define safe DB facts separately from public Native status. Pin a read-only offline `pg_controldata` inspection mechanism after stop (for example one exact owned inspector container with the original volume mounted read-only and no DB startup), unless the supervisor already preserves verified utility output before exit. Resource labels, volume identity and original deployment must come from the actual admitted plan. No C2 receipt field or readiness change belongs here.

### Bounded execution plan after probe and independent review

1. Prepare one fresh fixture token and ownership/cleanup manifest. Use G: for context/evidence and the established small protected C: fixture for isolated Core/Catalog/Host state; use no original data/keys/models. Reuse installed dependencies and build outputs. Pin the engine and new immutable task image. Do not mutate the accepted recovery fixture or its resources.
2. For the admitted candidate, use the real Core Run/Attempt/Effect -> Shell Gate -> protected Host -> Native grant/private submission path. Before admitted injection, assert that no database postmaster exists. After injection, require the original wrapper PID/startup evidence **and** a successful SQL connection. For the standalone candidate, explicitly record that these admission assertions are absent.
3. Record `server_version`, `SHOW data_directory`, `SHOW fsync`, `SHOW synchronous_commit`, `SHOW full_page_writes`, cluster system identifier (when supported by the pinned version), postmaster start time and actual process identity. Resolve the data directory beneath the one new named-volume mount; keep durability enabled. Use a fixed local socket/loopback connection with no published port and no external network.
4. Through a fixed task SQL probe, create one ordinary logged table and insert a small generated payload in a committed transaction. Retain the expected row ID/content digest outside the container, then verify it through a fresh SQL connection. Do not use a filesystem marker, temporary/unlogged table, `/health` or a running wrapper as the persistence test. The SQL probe is test data I/O, not a substitute custody/bootstrap path.
5. Stop **only the recorded original container**, with the reviewed outer timeout. Retain actual elapsed time/exit facts, actual database stop result, bounded shutdown output/control state, and absence of the owned postmaster. If using an offline inspector, it must run only read commands against that same volume. `shut down` is required; WAL recovery after a crash may preserve data but does not pass this graceful-stop case.
6. Start that same container with that same image and named volume, under the task's reviewed fault controls. Confirm a genuinely new Native startup and fresh tmpfs; observation alone must leave the database unstarted. Use `resumeStartup` for a fresh Run/Attempt/custody/grant to the original resource. Query the table **without recreating or reseeding it**; require the original payload digest and cluster identity, a new postmaster startup, and the same named-volume identity. A recreated cluster or a second seed fails. Production observer semantics remain inspect-only; this test restart does not add a production restart capability.
7. Scan the bounded owned image/container metadata, argv, registry/status/logs and persistent data for the fake sentinels, reporting counts only. Keep generated SQL payload separate from those sentinels. Perform the same graceful stop for cleanup; remove only manifest-owned container, unmounted volume, inspector and unique result tag/staging after evidence preservation. Retain unresolved identities after a timeout; no prune, daemon restart, original-container action or base-image deletion.

Suggested ceilings: one DB instance, one sequential read-only inspector if needed, <=1 MiB generated rows, <=1 GiB new DB/runtime storage, <=2 GiB G: growth, <=256 MiB protected C: fixture, no new H: build tree, <=60 seconds initial SQL readiness, <=30 seconds inner graceful stop, 45-second outer stop, and 15 minutes plus five-minute owned cleanup. For a standalone fixture, fixed 512 MiB memory/one CPU/64 PIDs are reasonable starting caps after checking the packaged runtime. The unchanged admitted adapter has no such CLI limits; do not pretend those hard caps apply there or inject arbitrary create options. Bound DB configuration/connections, monitor actual use, and stop on the reviewed limits. Reject a missing prerequisite rather than retrying with downloads or another daemon.
