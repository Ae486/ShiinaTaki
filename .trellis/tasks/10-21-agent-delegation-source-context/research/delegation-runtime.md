# Research: Official delegation runtimes and Taki integration

- Query: Which current official package primitives implement settled G1-G4, and what is the smallest integration into Taki's existing Runtime?
- Scope: mixed; official documentation and published package source, local static inspection, narrow deterministic probes.
- Date: 2026-10-21
- Task: `.trellis/tasks/10-21-agent-delegation-source-context` (session-scoped task supplied and verified by the coordinator). Legacy `.trellis/.current-task` points elsewhere and is not the routing authority.

## Findings

### Recommendation

Compose the existing AI SDK `ToolLoopAgent` and Core Run/Attempt/Effect, governance, history and scheduling owners. Use the coherently upgraded AI SDK baseline only after the separate compatibility investigation passes. Add bounded host integration for reusable child addressing, private working-history projection, message admission/consumption, independent cancellation and deduplicated completion. Retain one shared agent loop for parent and child.

Current `WorkflowAgent` adds substantial durable-loop functionality, and `HarnessAgent` adds real reusable native sessions, active-turn steering on several adapters, and continuation state. Neither establishes the entire G1-G4 contract without Taki integration. Harness is a wrapper around another runtime; sharing the AI SDK `Agent` interface does not make its native model/tool loop the existing Taki Runtime. Adopting it would require resolving different history and execution ownership. Workflow is a possible deliberate durability redesign, not a necessary child-manager dependency.

This is planning evidence, not framework selection, formal task activation, production implementation, accepted schema/API names, or completed acceptance.

### ToolLoopAgent: supported composition, not a native child manager

- Published `packages/ai/src/agent/tool-loop-agent.ts:44` stores configuration; `:145` prepares per-call settings/messages; `:203` onward delegates generation to SDK calls. `tool-loop-agent-settings.ts:165` provides `prepareStep`, `:241` tool execution callbacks and `:251` step-end capture. This is sufficient loop composition without another engine.
- Pinned [subagent guide](https://github.com/vercel/ai/blob/e6230e43ba9def164550eea562c457e23be9efa6/content/docs/03-agents/06-subagents.mdx) shows tool `execute` awaiting child generation, isolated prompt/history, preliminary output and `toModelOutput`. It also explicitly forbids approval flows **in that nested pattern**. Do not turn this limitation into permission bypass: independent Taki child execution needs its own existing Core Approval interaction.
- A delegated starter tool can return an honest work handle/admission acknowledgment while Core owns subsequent work/result. The exact tool shape is not selected here. If the parent later reasons over that acknowledgment, that is its current tool-loop behavior; G1 controls subsequent **child completion** inference, not every parent step that ever references a child.
- Runtime context reuse means replaying the child's own retained work plus explicitly supplied new input. It does not mean reusing the original Run's tool/Host/authority leases forever. Current `RunService` releases captured process context on terminal settlement.

### WorkflowAgent: real durability, substantial owner integration

- Pinned [WorkflowAgent guide](https://github.com/vercel/ai/blob/e6230e43ba9def164550eea562c457e23be9efa6/content/docs/03-agents/07-workflow-agent.mdx#L8) describes automatic persistence, model/tool steps, approvals and streaming through Workflow 5. At `:289` tool execution functions become durable by `'use step'`; at `:319` ordinary functions explicitly have no durability guarantee.
- `:516` explicitly forbids functions, class instances, Symbols, DB/SDK clients, WeakMaps/Sets in durable context. Taki captured tool closures, live authority/source checks and DB/MCP handles must be re-bound inside step owners by durable references. Serializing their apparent fields is not authority reconstruction.
- `:575` supports boundary message injection via `prepareStep`; this is still caller composition, not child inbox identity. `:838` describes durable model deadlines and SDK retry ownership; do not layer an additional uncontrolled retry mechanism around effects.
- Published `workflow-agent.ts:1196` documents queue injection at preparation; `:3674` distinguishes execute functions marked as workflow steps. Source has no demonstrated built-in retained child registry/G1 policy/stop-origin contract.
- Smallest credible adoption experiment would embed one governed deterministic fake tool and one mock model in Workflow on the supported local deployment target, use original Core Effect identity for an induced retry, and restart between model/tool boundaries. First resolve who owns scheduling, checkpoints, Attempts and authority. Current Windows deployment, Workflow build transform, local runtime storage and Core lifecycle parity are **not tested here**.
- `@ai-sdk/workflow-harness` is a separate optional package, not `@ai-sdk/workflow`. Its [utilities](https://ai-sdk.dev/docs/ai-sdk-harnesses/workflow-utilities) serialize harness continuation across steps; between user workflow runs the caller must persist `resumeFrom`, sandbox identity and re-bind host contexts. No installation or version-selection recommendation for that additional package is made.

### Two verified HA hazards

**Replay View:** `harness-agent.ts:939` selects the last user message from an entire input array. The exact-method deterministic probe supplied system snapshot, user task, assistant/private result, tool row and follow-up; the returned prompt was only the follow-up. Therefore swapping HA for TLA while passing Taki's existing `outgoing` silently discards prior Replay View material. Packing the snapshot into the latest user text is a new serialization/model-input design and does not preserve native role/tool framing automatically. Native history/compaction can also retain volatile input that ADR 0008 currently excludes from storage.

**Active stop:** `harness-agent-session.ts:542` takes `finalizeCurrentTurnSuspension` for any unfinished turn; `:650` calls `adapter.doSuspendTurn`; `adapter.doStop` runs only when idle. Probe results:

| Turn / sandbox ownership | Observed fake-adapter calls | Interpretation |
| --- | --- | --- |
| idle / caller-owned | `adapter.stop` | Between-turn stop reaches native stop. |
| idle / HA-owned | `adapter.stop`, `sandbox.stop` | Both lifecycle levels requested to stop. |
| running / caller-owned | **`adapter.suspend` only** | Exported state has continuation; no native stop was invoked. |
| running / HA-owned | `adapter.suspend`, `sandbox.stop` | Runtime suspension then infrastructure stop; not identical to independent turn cancellation. |

Codex `doSuspendTurn` explicitly keeps its bridge/model running (`codex-harness.ts:1315`). Hence published behavior with external sandbox conflicts with the broad docs description that `session.stop()` stops runtime. This probe proves control dispatch, not a live billing/process observation. G4c requires a tested per-child abort path plus retained continuity; do not use `suspendTurn`, `detach`, HA stop or UI stream closure as interchangeable Stop controls. Pi source further demonstrates that suspend can park a live host-input wait or abort/recompute on cold continuation depending on conditions.

HA built-in callbacks are another distinct issue: pinned Harness docs `02-harness-agent.mdx:164` say callback errors are ignored; `:166` says built-in start/end events occur after the runtime reports its result. They cannot be used as before-execution authorization or model Effect intent capture. Even callback sequencing before consumer-visible stream output is **after** the actual native effect.

## Caveats / Not Found

- No production/config/data changes, git operation, dependency install, model call, network sandbox, formal task activation, implementation dispatch or live child acceptance occurred. Writes are confined to this report and its `research/delegation-runtime/` evidence directory.
- Evidence downloads are official npm/GitHub metadata/source, not an installed working adapter. Narrow source-transpilation probes establish dispatch/reduction behavior only; external runtime support and real effect boundaries remain untested.
- Published adapter support can exceed or contradict pinned docs: Codex filtering/steer/app-server and Pi in-process parking are concrete examples. Re-pin exact packages for any later trial; metadata/version labels are not guarantees of platform compatibility.
- HA has real experimental active session steering; saying it has no steering would be wrong. Saying it provides a complete retained nested child manager from those methods would also be unsupported. Claude native child-related tools are present, but G1-G4 completion/stop-origin/retained-history behavior is not established through the adapter.
- No official generic HA fork/selected-parent-history import, per-child record-only completion policy or persisted stop-origin contract was found in the inspected public interfaces. This bounded negative is not a claim that upstream runtimes can never implement these behaviors.
- Do not promise stop from HA `session.stop()` on active externally owned sandbox: deterministic evidence shows suspension rather than native stop. Core exact cancellation requires independent proof; no speculative upstream patch or issue was submitted.
- Worker context continuity, restart authority reconstruction and external-effect reconciliation are separate. Current accepted-work hold/resume and prepared-publication child admission do not make generic child reuse/recovery finished.
- Detailed SDK migration and material serialization are owned by sibling research. Final storage/API fields remain unselected and must not be represented as individually owner-approved.
