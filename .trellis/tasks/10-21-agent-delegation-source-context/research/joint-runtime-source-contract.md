### 3. Identities and context selection

Use these distinct identities:

- `characterId`: unchanged owner of the one relationship Timeline and parent continuation lane.
- `subagentId`: Core-minted UUID for one private working continuity, scoped to one Character. Display names never address work. Its original `createdByRunId` records lineage, not authority/liveness.
- `inputId` plus monotonically increasing `inputSeq`: one accepted addressed message and its order within that child. The client/model operation key deduplicates submission; IDs are not inferred from text.
- `workInputId`: the already minted `inputId` of an `input_kind=work` record. It owns one delegated purpose and its captured completion policy across corrected/resumed executions. Every message/continuation names this exact work, and receives a monotonically increasing `workSeq` within it. No fifth work table or new task-management product is needed.
- `runId`: one admitted child execution. An idle/completed/cancelled child receiving authorized further work gets a new Run. `attemptId` remains the existing retry identity inside that Run.
- `completionId`: use the child `runId`; there is exactly one terminal execution result/completion record per Run. A separate UUID buys no additional identity.
- `parentContinuationRunId`: the separate Run admitted for that completion, if any. Original parent Run ID remains lineage even when terminal.

First delivery exposes main-Companion-to-Subagent operations; no peer messaging, shared task board or Team protocol is needed. Do not add feature-specific child reuse heuristics. The parent chooses new versus existing `subagentId`.

Proposed `WorkContext` port, owned by ChatAgent/Runtime (not an RPC shape):

```ts
type WorkContext = {
  scope: { kind: "subagent"; subagentId: string } | { kind: "parent-continuation"; completionId: string };
  initialMessages: readonly ModelMessage[];
  instructions: string;
  prepareStep(input: { messages: readonly ModelMessage[]; attemptId: string; stepNumber: number }): PreparedWorkStep;
  commitModelInput(step: PreparedWorkStep, intent: ModelIntentIdentity): void;
  // The commit above runs inside the existing model-intent transaction, not at prepareStep time.
  recordCompletedStep(attemptId: string, step: number, messages: readonly TurnMessage[]): void;
  recordPartial(attemptId: string, step: number, text: string): void;
};
```

`PreparedWorkStep` fixes the composed messages, newly selected input IDs, exact Attempt/step and `WorkToken`; `ModelIntentIdentity` carries the actual Effect ID and input digest (section 13). SDK message types stay Core-local. The port is distinct from `selectedContext`, does not overwrite disclosure, and never calls the primary witness sink. The target SDK carries selected step messages into subsequent steps, so `prepareStep` adds only not-yet-carried inputs instead of appending the entire inbox each time. The same ChatAgent owns governed tools, model Effects, telemetry, streaming, error/abort treatment and supported overflow retry.

Creation input chooses `fresh` or `snapshot` explicitly. A snapshot is the parent's selected current model-visible excerpts/summary/material, captured at accepted creation. It is not a lazy reference to `store.project(characterId)` at child dispatch. The Core selection helper must preserve complete native call/result groups when real structured history is selected; arbitrary text excerpts/summaries are marked supplied material, not fabricated user/assistant/tool records. A supplied summary remains generated context, not an original quote. Current clock, transient perception, memory authority, tool catalogs and credentials are not permanently inherited as authoritative configuration.

For a fresh child, use the current required Character/base instructions, captured governance/tools and explicitly supplied task/material. Do not add ordinary relationship history. For reuse, use that child's snapshot plus its ordered retained work and explicit new messages. Normal later parent chat is neither subscribed nor copied. Explicit material references remain available for later governed reads; no automatic preload of complete video/source content is required.

#### 3.1. Delegation configuration: instructions plus effective tools

Use two ordinary configuration inputs: the delegated task/role instructions and an optional tool selection. Instructions describe the job, working style, relevant context and expected result; they do not grant tools or permissions. A narrow role may use `toolSelection={mode:"allow", names:[...]}`. A general worker may use `{mode:"inherit", excludeNames:[...]}` or omit the selection to inherit the trusted permitted set. These are plain work-request fields, not a role registry, UI role-management feature, separate sandbox or new permission framework.

Compute the effective executable set at admission from the trusted parent's permitted capability/tool scope and the current captured registry: intersect an allow list (or start with the inherited set), apply requested exclusions, then always remove child Memory mutations. Resolve actual registered tool identities/names and existing operation/capability metadata; a model-supplied name cannot add a tool outside the trusted available set. Refuse invalid/unavailable explicit selections with a typed result instead of silently widening them. Persist this optional selection as `tool_selection_json` on the existing work input (covered by its request digest), while task/role instructions remain ordinary `direction_text`. No separate role configuration record is needed. Normal admission/snapshot lifetime rules still govern recapture on a later Run.

Reuse the existing captured tool snapshot and ChatAgent's final `allowedToolNames` filtering over the assembled ToolSet, after Core/memory/captured/Skill tool composition. This actual set is what the SDK looks up to execute a call; `activeTools` only selects disclosure from it and cannot restore omitted tools. Keep the resolved selection immutable for an execution and preserve it across its retries; a later work request can select differently under current authority. Existing governance continues to authorize/approve/record the tools that remain. Do not add a second permission check service, parallel role policy table or redundant dispatch wrapper merely to repeat the same membership decision. Only a demonstrated route around the effective lookup requires a targeted fix in its existing owner.

#### 3.2. Child Memory is read-only; main continuation retains its authority

The existing mechanisms support the required restriction, but it is **not already enforced** for generic children. `ChatAgent.finishRecordedTurn` and non-primary `afterCommit` avoid primary persistence/automatic maintenance, while `assembleTurnTools` still chooses `runContext.memoryTools ?? deps.memory.createTools(...)`. `run-snapshot-capture.ts` currently captures full `memory.tools` except for the initiative-specific recall projection. Therefore no-automatic-ingestion and read-only tools are separate requirements.

Derive the fixed child Memory exclusions from the existing trusted work scope: `subagent` is read-only; `parent-continuation` represents the main Companion and uses its normal permitted tools. No separate mutable `memoryAccess` policy service is needed. Do **not** infer this from `request.initiator==='subagent'`, since both executions use that initiator. Public/model input cannot promote a child to main scope. Reuse/retry/recovery derives the same exclusions from exact linked execution ownership before exposing tools; an unproven recovered scope refuses execution rather than defaulting to full access.

A small assembly helper uses `memoryEffectMetadata(tool).operation` (`recall|reflect` versus `retain|edit|invalidate|restore`) and the existing canonical classification. `core-tool-governance-adapter.ts` maps `recall`/`reflect` and supported legacy `memory_search` to `core.memory.search`, writes to `core.memory.write`, and invalidation/legacy archive to `core.memory.archive`. Preserve non-enumerable metadata through tool wrapping/copying; classify actual operations/capability IDs rather than display names. Child executable lookup excludes mutations, including any actual alias carrying that operation/classification, even when requested in an allow list. Skills/disclosure/reassembly must operate within that final set. Existing governance and unknown-Core-tool refusal remain in place; no duplicate Memory authorization layer is introduced.

Keep `RunMemoryReference` provider capabilities and `capabilityDigest` unchanged: they describe actual provider support and participate in authority/drift/call-option checks. Rewriting `retain/edit/etc` to false would falsify the snapshot. The child context always supplies an explicit projected `memoryTools`, including frozen `{}` if no reads are available; `undefined` would select ChatAgent's full-tool fallback. Likewise a completely empty effective tool selection remains an explicit empty set/`allowedToolNames:[]`, not an omitted filter. Enforce membership in the actual assembled executable lookup, not merely prompt text or `activeTools` disclosure.

Reuse current allowed/relevant Memory assembly, automatic recall and read tools, including permitted Local/Hindsight recall/reflection and supported legacy search. Do not import the initiative-only selected-topic/one-attempt/quota behavior from `createInitiativeMemoryRecall`; its captured read projection is a pattern, not the child's product policy. No automatic ingestion of child/private/parent-continuation rows is introduced. Children cannot retain, edit, invalidate, restore, archive or otherwise mutate semantic long-term Memory. They may return proposed changes as ordinary result data; only the main Companion decides and acts under its normal existing authority. Child transcript/Effect/result writes are Runtime evidence, not semantic Memory changes.

Prompts state this role boundary and ask children to propose useful corrections instead of applying them. Main prompts/maintenance authority are not globally restricted. If an actual exposed workspace/Host tool is demonstrated to reach a canonical-memory mutation, account for that route through its existing governance classification; this requirement does not authorize an invented OS-wide sandbox redesign. Acceptance covers real executable reads/denials for canonical Local, Hindsight and the supported legacy path, including empty projection, aliases/metadata, Skill disclosure, retries/reuse/reconnect/recovery and main-continuation write availability.

Child replay uses the existing tool-group window/reduction/token helpers over private rows. Keep the complete durable transcript queryable. If a bounded replay cannot include old work, expose an omission/reference fact and the child-history read tool; never strand tool results or claim the omitted context was supplied. Do not reuse Character summary rows with a fake Character ID or build a second compaction engine in this slice. Primary/publication compaction is included below; additional private-child rolling summaries require an actual pressure case and a separate small reuse of the existing coordinator.

`completion_state` is `not_requested|pending|deferred|admitted|withheld`. These are notification/admission facts, not Run states. `deferred` has a typed reason such as foreground busy, source unavailable or authority unavailable; `withheld` records definitive supersession/retirement. `parent_run_id` is unique when non-null. A result body can be absent because no output was produced; `result_json` still records the terminal report with nullable body and source context. Terminal completion with no content is not an empty successful answer.

The work root captures `work_expires_at` once from the required `lifetimeMinutes` (5–720) at accepted input creation, including work still waiting for its first Run. Requested lifetime participates in the immutable request digest. Same-work messages, continuation and retries retain that expiry; a duplicate operation returns the original value and a changed lifetime conflicts. Linked execution deadlines cannot exceed the accepted expiry. Only a new work root captures a new lifetime. This makes section 5's lifetime contract explicit in the S1 storage handoff; it introduces no new scheduling policy.

The repository atomically allocates child-global display sequence and exact work sequence and returns both. Conversation `control_version` fences child stop/continue and active ownership changes; accepting independent queued work B must not change active A's control token. `active_run_id` is a coordination reference checked against the exact linked Run/Attempt; set/clear it transactionally and allow only one nonterminal execution per child. A terminal pointer release does not release a still-held execution lane/controller before its owner's `finally` has quiesced.

`work` creates a new `workInputId`, even when it reuses an existing child. If A is active, B waits without changing A. `message` and `continue` require the exact work target; a UI convenience may resolve the displayed active work only with its expected Run/control version, and persists that resolved target at acceptance. A message sent after B is queued does not silently become a message to B or to A. A same-work late correction gets a higher `workSeq` and can require a new execution of that work; its policy is inherited from that work root, never the newest other work. `continue` also requires the correct stop/recovery control and a quiescent predecessor. The scheduler may batch only consecutive addressed messages belonging to the same work. Independent B cannot consume or supersede A's completion. This slice does not add a generic replacement action: replace A by explicitly stopping/correcting A, not by merely reusing its child for B.

Do not persist raw SDK prompts, system instructions, provider options or credentials in RunSnapshot/events. The selected private context stores the same permitted material/structured message representation needed for replay, with existing tool-input privacy, source fencing and attachment rules. Full model reasoning/hidden chain-of-thought is not a transcript deliverable. Completed tool-call names/IDs/results and visible assistant text are.

Two narrow linked-write seams are required in existing Run persistence:

1. **Admission:** extend the internal Run admission path with a trusted synchronous linked-write participant. Async capture finishes first; revalidate exact child control/work input/source and capacity; inside `RunRepo.admit`'s transaction insert Run/Attempt/snapshot/events and the corresponding execution/active pointer, or set the exact completion's `parent_run_id`. Publish events and start work only after commit. On duplicate key, verify linkage and request digest and return the original admission without dispatch. This is internal Core code, never a callback from RPC/model/extension JSON.
2. **Every terminal path:** install one configured linked-state participant inside canonical private `run-repo.ts` `settle`, after computing the final target and inside the same transaction as Run/Attempt/receipt/events. Public `settle` may change completion to deadline expiry; the private function may change it to cancellation. Pass that final target to the participant. `RunRepo.start` cancellation/deadline/budget refusal, `guardDispatch`, ordinary `RunService.settle`, and recovery's direct repository settlement all reach it. It commits the final private batch, honest result/outbox or linked parent result, and exact active-pointer release. It must not depend on a disposable RunExecutionContext callback, which is absent at boot. Failure rolls back all terminal state. Duplicate/stale terminal calls cannot rewrite results.

Persist a result proposal keyed to exact Run/Attempt and WorkToken before asking to settle (domain validation and filesystem reads finish outside SQLite). A proposal is not a success report. Canonical terminalization accepts it as final only when final outcome, token and validation permit it; cancellation/deadline/unknown outcomes preserve useful partial/proposed evidence but never a success-shaped answer or publish decision. Without a proposal, terminalize to an explicit no-output/partial/status report. Recovery may use only persisted validated proposals/step evidence, not rerun a model to reconstruct an answer. For parent-continuation Runs, the same participant finds the completion row by `parent_run_id` and records its synthesis/disposition. Post-commit terminal notification also disposes the exact captured Run resources idempotently across direct repository paths; it cannot change committed outcome or prematurely grant a busy lane.

The existing model-intent hook demonstrates this synchronous transaction-participant pattern. Do not implement it as an outer transaction around a repository call whose live events have already been published. A COMMIT failure must publish neither success events nor a wake. Reuse the database wrapper's rollback/savepoint guarantees.

Completed private steps are persisted through `onStepEnd` before a subsequent model request. The shared recording utility continues to capture observed partial text on graceful abort, thrown abort, later provider error and iterator close. Partial text is explicitly partial and never a final success/result. A hard process kill can lose an uncommitted current-step fragment; completed persisted steps remain inspectable. Duplicate step capture compares identity/digest and never appends it twice.

### 6. Scheduling, addressed-input consumption and stop semantics

**Queue ownership.** Preserve existing relationship keys (`characterId`) to avoid changing all primary/initiative consumers. Add a single internal key helper for child lanes such as `subagent:<UUID>`. The scheduler retains independent child work promises/controllers beyond the parent tool return. It uses the existing TurnQueue instance and filters its hooks: primary/release Character callbacks receive actual Character keys only; child releases notify only the child owner. Parent continuation uses the normal Character background acquisition, so pending primary reservations win. Publishing continues through the Character lane/DeliveryCoordinator. Never hold one child lane while awaiting another, and never synchronously wait for child completion inside the parent's held Character lane.

**Registry ownership.** Extend TurnRegistry to register exact work scope plus Run identity, with a `runId -> controller/scope` index and one active controller per work scope. `begin` refuses a different live controller in an occupied scope instead of silently replacing it. Existing `cancel(characterId)` means the Character execution only. Exact cancel validates Character and scope. `chat.cancel` with a linked child Run routes through SubagentService user-stop, including the latch; it must not become a bypass. `drain` enumerates every scope on actual Core shutdown.

**Capacity.** Reuse each Run's step/deadline/budget limits. Conservative initial internal limits are four active children per Character and sixteen process-wide; these are unmeasured scheduling defaults, not limits on retained child creation. Refill fairly across queued work on real releases; accepted work remains durable, with visible queuing latency. A full pending-input buffer refuses before acceptance. Do not truncate source/results, cancel work or introduce feature quotas to enforce capacity. This adds bounded admission to the existing owner, not another scheduler/runtime.

**Input boundary.** Each accepted message has ordered sender/direction/material facts. If active, it becomes eligible at the next ToolLoopAgent `prepareStep`, not inside an already dispatched request or an arbitrary running tool. Compose the existing `activeTools` disclosure result with the updated message array; do not replace disclosure, bypass governance or create a second loop. A prepare callback may run without a provider call: merely selecting an input is not consumption.

Freeze the selected same-work input batch, Attempt and step. Extend the existing internal intent callback to receive the prepared Effect ID/Run/Attempt/input digest (existing no-argument guard/charge callbacks can ignore the argument). In the actual Effect transaction, verify active ownership, stop token and trusted source revision, record exact per-Effect input receipts/private insertion, and fill first-consumed fields only if absent. The callback and Effect insertion share one commit; use a deferred FK if the callback inserts a receipt before the Effect row. A message arriving after selection remains pending, rather than making receipt of the earlier selected batch a lie. A source-changing correction can independently invalidate the trusted revision and refuse dispatch. Label receipt “included in model request intent”; it proves neither provider receipt nor model understanding. Provider retry/overflow Attempts retain separate Effect receipts without creating another addressed message or duplicating it in logical replay.

If A returns a final result before a pending message **addressed to A** was selected, persist it with A's `through_work_seq`, withhold it as superseded for automatic continuation/publication, then schedule A's correction as a new execution after lane release. An independent queued work B is not such a message: A's result/policy remain valid and B waits its turn. Do not append a phantom SDK step. Completion admission checks work identity, that work's latest required watermark and relevant source revision; it never compares against the child's global newest input, unrelated work or ordinary parent chat. An old A report remains discoverable by work/completion ID even if B is now the child's newest work.

`WorkToken = { subagentId, workInputId, throughWorkSeq, controlVersion, source?: { ownerRef, revision } }` is an immutable captured token, not executable authority. Its live trusted port returns `current`, `unavailable(reason)` or `retired(reason)`/`superseded(reason)`. At model intent it checks exact active Run/control/source and permits later unselected messages to stay pending. At result finalization/parent admission/publication it checks that exact work's required watermark/source; it does not require that work to still be the child's active/latest work, or that an unrelated later child stop has the old control version. Readable source labels/hashes cannot implement this port, and restart cannot reconstruct its live authority from JSON alone.

| Event | Active execution | Retained context / later work | Completion policy |
| --- | --- | --- | --- |
| Parent chat stop/disconnect | Cancel exact parent only | All accepted children continue under their own controller and limits | Unchanged |
| User stops child | Atomically latch user stop and request exact Run cancel; then abort its controller | Preserve all inputs/history/results; later parent input can be recorded as blocked but cannot dispatch | Original policy retained; any terminal report is honestly labelled cancelled/partial |
| Parent interrupts child | Latch parent stop and cancel exact child | Parent or user explicit continuation may clear it and admit a new Run | Original execution policy retained; new work captures its own |
| User continues child | CAS clear user latch; admit only after old execution is quiescent and recovery permits it | Same `subagentId`, new Run after a terminal predecessor | Explicit/new-work resolved policy |
| Source revision changes | Close the source-dependent output gate before any external edit; cancel/withhold only affected work according to its existing owner | Old evidence remains historical; new input binds the actual new revision | Intent unchanged; stale result cannot be treated as a current result |
| Core shutdown | Seal admission, stop pumps, drain all scopes, release resources | Restart classification determines continuation; no survival promise for in-flight effects | Durable intent remains, dispatch still needs valid authority |

A stop latch also applies when a child is idle: a later addressed message cannot race past an idle user stop. A parent interruption cannot downgrade a user stop. Stop/continue responses carry the resulting control version. UI stale version/reconnect errors require a fresh state read and deliberate action, not an automatic resend.

### 7. Completion and parent admission

The terminal report uses the authoritative Run outcome and nullable final/partial output. Normal completion, failure, cancellation, deadline and unknown outcome are all inspectable. The `request_parent` choice requests one status-bearing parent continuation for that terminal report, subject to the gates below; cancelled/unknown reports are never successful child answers. The parent's tools still cannot resume a user-stopped child. This consistent terminal-notification default avoids inventing a second failure-only notification policy; it is a technical choice for the independent review, not an extra promise of speech.

Algorithm:

1. Child finishes or fails. Commit its actual private output, Run terminal state and immutable result in the same settlement transaction. Set `not_requested` for record-only; otherwise `pending`. A duplicate callback returns the original result and never creates another outbox item.
2. Post-commit notify the existing Core composition's child-completion pump. The durable row is the queue truth; an in-memory notification is merely a hint. Boot and Character-lane release scan bounded pending/deferred rows. Do not put them in WakeEngine's one C1 pending slot.
3. Read exact work/result token. A correction to that work or its actual source may withhold it; unrelated queued B cannot. Temporary source/authority loss is `deferred`, definitive retirement/supersession is `withheld`. Foreground busy is a deferral, not lost completion.
4. Acquire the normal Character background lane and recheck that work's token/current source. The original parent Run may be stopped/completed: that alone is not a refusal. Do not use its abort signal, active Attempt or held lane as new authority.
5. Admit one new Run with `initiator=subagent`, `deliveryClass=internal`, `contextMode=autonomous`, provider marker `core.subagent-completion`, original lineage and immutable `payloadRef` for the completion. Stable idempotency key: `subagent-completion:<childRunId>`. Atomically link the outbox to this new Run at admission. Capture current permitted Host/governance/memory context; never copy expired executable closures. The delegated purpose/source validity is checked separately from the old parent request's liveness.
6. Use the same ChatAgent with current relationship Replay View plus the exact bounded completion report as Core context. It is not a user statement or fabricated tool result. Persist internal work in `run_messages` and the terminal parent result on its linked completion row; call no primary witness sink. `subagent.result`, history and list summaries expose that parent Run/result and disposition.
7. A dedicated `finish_parent_continuation` collector chooses `internal_result {text, materials?}`, `no_action {reason, text?}`, or `reply {text, materials?}`. The schema has no class, acceptance, arbitrary root ID or authority fields. A reply choice is available only when the Runtime has bound a real reply adapter. The collector records a proposal; canonical terminalization records the final result. Only a completed, valid explicit reply proposal is handed to its bound adapter after commit. Plain streamed text remains inspectable as `unstructured` output, not an implicit reply or a fabricated no-action decision.

For a primary parent that explicitly invokes `inspect_subagent`, return the result as the real tool result with its actual call identity. `toModelOutput` must keep outcome, generation and selected material meaning; it cannot reduce the result to bare `text`. For automatic completion in a new Run, use the Core context envelope rather than a fake delayed tool result.

An existing publication owner may consume the child's validated result without a parent call (Co-Watching uses `record_only`). Its authority remains external to completion. For an ordinary direct user research request, the following concrete adapter supplies the full delayed-answer path rather than leaving the useful synthesis in raw private rows.

### 8. Minimal generation/material source contract

Operational validity and readable source description are different values. Reuse the existing source/candidate/revision/Host/consent/expiry authorities for dispatch decisions. A descriptive source field, URL or hash is never an authorization or currentness proof.

Proposed Shared data shapes:

```ts
type MaterialSource = {
  label?: string;       // existing provider/source/title label, when useful
  reference?: string;   // existing usable document/media/message reference
  speaker?: string;     // supplied/displayed identity, never inferred from "I"
  time?: string;        // known source time or locator, not a generated date
};
type GenerationOrigin = { runId: string; attemptId: string; subagentId?: string };
type SourceContext = {
  generatedBy?: GenerationOrigin;
  materials?: readonly MaterialSource[];
};
type ContextMaterial = { key: string; text: string; source?: MaterialSource };
type MaterialRef =
  | { kind: "input"; inputId: string; key: string }
  | { kind: "tool_result"; runId: string; attemptId: string; stepNumber: number; toolCallId: string; key: string }
  | { kind: "retained_result"; childRunId: string; resultDigest: string; materialIndex: number };
```

`ContextMaterial.key` is local to one supplying record. Input-owned keys include the creation seed; tool-owned keys include exact Run/Attempt/step/call identity, so repeated call IDs in another step cannot alias a source. `retained_result` lets parent synthesis select the immutable descriptors already supplied by that child completion, without copying the private transcript or inventing an addressed input. It resolves only that stored result's flat material array, never traverses a provenance graph. Structured history keeps its real native pairs; selection can address known source descriptions on the existing result or copied seed description without forging a new tool call. `SourceContext` is an optional material-level output/candidate/row sidecar. New result generation is program-known; legacy unknown origin stays absent. Publication Run identity remains separate from original generation.

#### 8.1. Tool-acquired material registration

A governed capability/result adapter may call the Core-local `registerToolMaterials({runId,attemptId,stepNumber,toolCallId,materials:[{key,source}]})` port after obtaining its actual result. Identity is supplied/validated by the live governed invocation, not by model arguments. The callback records only facts the adapter already knows (document title/ref, media/time/speaker when supplied). It does not parse arbitrary prose to infer authorship. Bind these descriptions to the matching real completed tool-result part in the private step transaction. Extend that part with an optional `sourceMaterials` sidecar (also supported when selected primary-history parts already have one); raw tagged output, native name/ID and success/error/empty value remain unchanged. No new table or global material catalog is introduced.

Before the next SDK step, the common renderer projects the source description and selectable `MaterialRef` beside its actual tool result. A small native output that already expresses the needed source can keep that framing; no duplicate prose wrapper is required, but selectable registered keys still have an unambiguous bounded projection when needed. Source registration without a matched result is not evidence of successful reading. Failed/unavailable results retain their real outcome and may describe the attempted source, but cannot be selected as a successful factual read. A verified empty result remains an empty successful read, distinct from failure.

The final collector validates each selected ref against this child/parent working context: explicit input, actual retained governed result, selected inherited history or exact supplied completion. Copy only the selected known descriptors into the immutable output, preserving absence for unknown-source tools. After reuse/restart, resolve from the retained parts/sidecars, not an in-memory registration map. Live source validity/retrieval authority remains separate. The `renderSourcedToolResult`/reduction port treats body/status plus necessary source header as one unit: preserve the header with surviving content, or replace both with a truthful status/omission/reference trace. Never flatten away the only attribution while leaving first-person prose presented as unsupported user experience.

All four MaterialSource fields are optional. An absent field means unavailable/not supplied. Omit an empty source object. Absent `materials` means no declared material mapping, not “proved independent of external material”; an empty array is normalized to absent. Do not infer speaker from first person, infer URL from a filename/hash, or require identical metadata from video, screenshot and QQ material. A provider can include additional useful existing descriptive facts in its own material text without expanding this common schema. A reference need not be globally dereferenceable; if later detail retrieval fails, report unavailable while retaining the immutable useful description.

**Selection and inheritance rules:**

- Program facts come from the supplying capability/adapter, exact selected input or actual governed tool result. A model selects `MaterialRef` values and explains its interpretation in ordinary text; it cannot mint trusted facts/currentness. Validate refs against retained working-context evidence before copying known descriptions.
- Do not automatically attach every material available to a Run to every result or utterance. Attach only a material group actually selected for that result/candidate. Several materially different portions can be separate result sections if needed; no mandatory sentence-level citation scheme.
- Selected material metadata means “this supplied material informed this generated item,” not proof of each claim. Natural language and shared prompts still identify who experienced something and what is inference.
- Ordinary primary assistant replies retain native speech. Where the final reply has no explicit material selection, do not invent a complete material mapping from all previously seen tools. The source-aware prompt must preserve relevant attribution in its actual wording; the original nearby native tool evidence remains available to replay/compaction. A primary reply that has already erased its subject is a semantic failure, not something downstream storage can reconstruct reliably.
- A Co-Watching candidate can deterministically inherit the exact accepted media/native result and its already validated `momentId`, because those are explicit candidate inputs. Store a human-readable label/reference/time locator when available; do not interpret the moment's life story in program code. The generating Run/Attempt is known from preparation. The source child's implementation adds this bridge before generic candidate narrowing.

Initial rendering rules:
