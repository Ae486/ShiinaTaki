## Findings

### 1. Decision and sequencing

**Prepare D1 in parallel with C2b; retain actual dependencies at their consuming boundary.** The 2026-10-07 study's blanket `C1-C3 -> D1` ordering is too broad for untouched same-version restoration. It is also stale about 5B: `T/.trellis/tasks/10-07-hindsight-template-lifecycle/research/b3-whole-acceptance.md` accepts all eleven automatic criteria, including customized/removed paired restores with exact rows across 61 Native tables. This is historical accepted evidence, not a new runtime check.

The smallest coherent D1 deliverable is a complete, immutable-source, **same-version PostgreSQL-backed paired restore**, independently owned and recoverable by its original candidate identity, followed by candidate-bound read-only verification. Preserve logical lineage, Bank IDs/generations, original Core authority epoch, receipts and template history. Give the physical candidate a new deployment/resource identity; do not mint a replacement logical authority or rewrite historical signatures.

Three review boundaries avoid false completion:

1. **Source/deterministic foundation:** candidate schema and persisted ownership, strict inventory, unchanged-version restore adapter, original-request recovery and the existing immutable Core reader can be implemented/reviewed without a working C2b API or full C3 apply. Current authorization is planning only; later implementation still follows Root's gate.
2. **Actual isolated archive baseline:** a real owned PostgreSQL target, strict restore and complete inventory/byte/row verification can run with its API/workers stopped. This may produce `restored_unverified`; it cannot satisfy the existing selected-template authenticated observation contract.
3. **Actual verified D1 candidate:** requires the exact candidate-bound authenticated observer, safe installed Host/custody/resource control and an archive-compatible no-inference profile. Consume C2b's accepted producers where used. Full six-slot **application** is unnecessary for an unchanged, nonexecuting copy; any claimed model semantics/readback must have its own real producer. Unknown model metadata remains explicit and blocks model-dependent execution/handoff, not archive preservation itself.

C2b's planned `managed-api-initial-v1` profile has unused embedding metadata (1536), no LLM and `rrf`; it is not automatically suitable for an arbitrary populated archive. Reusing that profile as proof of original embedding identity would violate the requirement. D1's eventual supported profile must preserve the archived schema/vector dimensions and template tenant context without inference or startup transformations. Never rewrite original metadata to match C2b defaults.

### 5. Smallest durable ownership and state contract

Use the existing three owners with one narrow new domain record; avoid an orchestration framework:

- **Core Memory Operations** owns the operator request, canonical original request/plan hash, candidate status and immutable baseline evidence. Add a candidate document/repository linked to its operation, because existing small producer refs and Host registry do not contain archive identity/full inventory/verification. Preserve source backup and domain IDs. Reuse operation admission, original-result lookup, checkpoints and readonly boot classification.
- **Existing Core Run/Attempt/Effect + Gate** owns each Host-bound action and its issued/accepted provenance. The candidate document references those actual IDs; it must not invent trusted handles from public JSON. Candidate operation ID and Host deployment/Run ID may be different and need explicit linkage rather than forcing unrelated ID domains equal.
- **Installed Host** owns fresh resources, protected registry entries, restore dispatch fence and observed physical results. Extend/version the existing protected registry format to retain an independently keyed candidate resource record alongside the selected deployment; do not overwrite its singleton source record or create a second unsynchronized registry writer. A bounded candidate map in that same owner/lock is sufficient for D1; no general multi-deployment scheduler is justified.
- **Native restore/observer** owns database transaction and fresh observation evidence. It never selects Core authority. Keep a stable restore-operation marker in candidate-owned administrative metadata outside copied domain tables, or another transactionally correlated completion proof, so a lost restore reply can be distinguished from committed/rolled-back/unknown work. The Host fence alone proves dispatch, not PostgreSQL commit. Do not replay truncate/COPY to resolve uncertainty.

Prefer a small candidate-only administrative receipt committed in the **same PostgreSQL transaction** as COPY, binding candidate/restore request/archive identity. Keep it in a distinct candidate administrative namespace outside the restored source schema, explicitly classified in the candidate inventory; do not append an invented historical row to the archived domain. A narrow connection/transaction helper extracted from `_restore` can allow this while preserving the ordinary CLI wrapper. This is a proposed new seam, not a present API. It gives lost-reply recovery direct commit identity without a new global Native migration. Full-row readback remains mandatory. The alternative is equality-only reconciliation: fewer administrative objects, but stronger provenance requirements to establish that unchanged rows represent this original restore, so it is less direct for operation recovery.
