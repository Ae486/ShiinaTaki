## Prompt diagnosis on the owner's challenge

The owner correctly asked whether the prompt and interaction design were inadequate before considering a change of
thinking mode. Checking only that a tool and one system sentence existed was insufficient causal analysis.

- Complete worker request inspection and `agent-attempt.ts` confirm no main Companion persona/Memory prompt leakage:
  the child branch uses private worker instructions plus Host/extension metadata and the date.
- The parent asks for plain text, a table, or `Case / Verdict / Reason`, while the worker protocol merely says
  `Use complete_subagent for your final report`. It does not explicitly map the requested format to that tool's
  `text` argument. Identical wording succeeded and failed, so an output-channel ambiguity is identified, not proven
  as the sole cause of omission.
- A stronger interaction ambiguity is directly observed: the parent framed a deliverable as
  `STATUS: awaiting clarification / QUESTION TO OWNER / NEXT`; the child submitted that report through the completion
  tool instead of opening a wait. Calling any tool is therefore insufficient; the correct lifecycle action matters.
- Minimal candidate: clearly distinguish whole-job completion, required-input waiting and ordinary progress; state
  that report-format requirements apply within tool `text`, and that a clarification stage does not finish the whole job.
  Production prompts remain unchanged while this is discussed and tested.
- A controlled first-response pilot replayed two saved synthetic tasks twice with baseline and clarified protocol
  wording, leaving model, default thinking, task data and tools constant. Baseline 4/4 and clarified 4/4 selected
  `complete_subagent`. This eight-call pilot did not reproduce the omission and provides no demonstrated improvement;
  no tools were executed, so it is not end-to-end acceptance. Inputs/results: `prompt-protocol-pilot/` under the validation root.
- API `tool_choice=required` means at least one tool call per model step, not guaranteed final completion or correct
  tool choice. The unchanged configured route rejected it with HTTP 400 mentioning thinking/tool choice. A separate
  one-request counterfactual with thinking disabled accepted it and returned a tool call (349 reported tokens).
  This establishes a provider compatibility tradeoff, not comparative reasoning quality. No Runtime or production
  configuration was changed; `required-tool-probe.json` and `required-tool-probe-thinking-disabled.json` retain evidence.
