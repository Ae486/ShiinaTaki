## Hidden-row forward-cursor candidate — no required correction

The old minimal adapter correctly showed that an arbitrary row becoming visible below an exhausted forward cursor can be missed. That adapter did not establish when an external Desktop read could observe the required intermediate state in this application's producer.

Current production sequence:

1. `run-message-store.ts:107-116` synchronously commits output/collector evidence and calls `changed`. `subagent-conversation-repo.ts:94-101` withholds output rows while the active Run still lacks presentation sidecars. This synchronous hidden window is real and was freshly observed.
2. `subagent-execution.ts:49` immediately drains the actual child agent iterator; it does not await a UI/client acknowledgement or external work between deltas. `agent-attempt.ts:188-195` routes the same SDK stream into child activity. `subagent-activity.ts:43-46,69-81` persists presentation references synchronously when finish-step is consumed and emits the existing invalidation.
3. `subagent-subscriptions.ts:33` coalesces notifications through a microtask. The Desktop's conversation endpoint is external operator RPC (`server/methods/subagent-methods.ts:31`), not a reentrant query inside the synchronous completed-step callback. There is no production callback here that holds that hidden interval open for an incoming socket request. The SDK and current drained consumer can supply presentation before the next incoming event-loop read.

The new probe uses unmodified actual SDK/ChatAgent/SQLite producers and `SubagentConversationPages` against the real `service.conversation` projection. It observes `changed` synchronously, at its queued microtask, and at `setImmediate` read opportunities. It also sends a burst of 60 actual addressed inputs through `service.send` while the child is running. This supplies more than the real 50-entry newest-page size without fabricating sequence rows or delaying presentation artificially. Two variants exercise 30 tool steps plus completion, with and without text-delta yields through the actual nested async generators.

Both caches finished with `hasMore=false`; the final comparison traversed all actual Core newer pages. Their read counts were 63 and 174 respectively. Neither fixture reported errors. Reads run on the Core event loop with direct service adapters, not a native browser/actual socket; the external-RPC scheduling relationship is separately verified in production source. The previous synthetic candidate is therefore not promoted to a bug and needs no speculative paging repair for this source.
