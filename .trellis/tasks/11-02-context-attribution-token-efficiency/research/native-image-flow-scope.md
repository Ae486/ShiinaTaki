# Research: Native image flow and removal of separate vision translation

- Query: Map actual image delivery and the smallest migration that sends all images directly to the main conversation model, removes the separately configured vision model and image-to-text translator calls/prompts, and preserves capture, storage, consent and source responsibilities.
- Scope: mixed; live workspace source and installed SDK/provider source, with no model calls or production mutation.
- Date: 2026-11-02
- Workspace: `H:/TakiAgent-worktrees/t4`; parent verified branch `task/t4-skills-mcp-productization` and session-scoped planning task. The dispatch path governs this artifact; the child-local legacy `.trellis/.current-task` is not the session authority.
- Ownership: this research file only. Findings and migration suggestions remain hypotheses for independent parent/child verification.

## Findings

### Decision and current behavior

**Use the separate bounded native multimodal task for implementation.** The owner clarification covers user attachments, explicit agent screenshots, ambient sampling and selected viewing evidence. Keeping either translator but changing its injected model to the main model does not meet that requirement. The parent created `.trellis/tasks/11-02-native-multimodal-model-capabilities` in planning; link this evidence there without duplicating it.

The incoming user-image path is already native. `agent-attempt.ts:68` chooses the optional vision model for an image-bearing turn, then the same `ToolLoopAgent` handles instructions, tools and streaming (`agent-attempt.ts:93`). `buildOutgoing` and `buildMultimodalUser` construct native user `FilePart`s from the original base64 (`agent-attempt.ts:243`, `agent-attempt.ts:280`). There is no foreground recognition-text-before-answer stage for these attachments. The extra image recognition is a detached post-commit memory call (`agent-attempt.ts:230`, `chat-agent.ts:326`, `main.ts:280`).

Screenshot and ambient paths really do translate pixels to text before main reasoning. `screenshot-tool.ts:69` invokes `describe`; `ambient-observation.ts:31` invokes it before publishing a screen description; `viewing-invitation-evidence.ts:63` invokes it before supplying unsolicited viewing evidence. These consumers must migrate, rather than disappear or keep that handoff under a different model name.

### Native support: sufficient SDK building blocks, incomplete application wiring

Installed versions, read from local package metadata: `ai@7.0.148`, `@ai-sdk/openai-compatible@3.0.75`. The factory header's older `3.0.5` reference is not the current installed version.

- The application already builds user `FilePart`s. Installed provider source converts image data to native `image_url` parts and creates its own data URL at the HTTP boundary: `packages/core/node_modules/@ai-sdk/openai-compatible/src/chat/convert-to-openai-compatible-chat-messages.ts:76`. Do not confuse the API's raw-base64 input with that final transport encoding.
- **Multimodal user support does not imply multimodal tool-role support.** The same converter defaults `supportsMultiPartToolContent=false` (`:194`), and a `content` tool output is JSON-stringified unless enabled (`:317`). `provider-factory.ts:21` does not enable it. Adding image bytes to a tool result's JSON or `toModelOutput` alone can therefore send base64 as ordinary text rather than an image.
- The provider exposes the multipart-tool setting (`packages/core/node_modules/@ai-sdk/openai-compatible/src/openai-compatible-provider.ts:100`), but local source support is not evidence that the owner's actual gateway accepts images in a `tool` message. Native **user** image parts already have an implementation seam and are the narrower default to verify for screenshot follow-up requests.
- `provider-config.ts:10` accepts endpoint/key/model only. The current loaders and factory have no explicit main-image capability declaration. The owner reports current model support; no live main-model image call was made here. Coordinate that conditional admission with the separate capability researcher, without building another model catalog in this work.

### What survives later turns and restart today

1. User Timeline rows persist caption plus image refs, not bytes (`turn-mapping.ts:32`). For an empty caption, their display projection is `[image]`. The files live at `dataDir/workspace/attachments` (`main.ts:270`).
2. `attachment-store.ts:99` confines refs before filesystem access, and `:106` reloads raw bytes. Files survive restart until removed by TTL or operator clear. TTL is based on mtime (`:74`); a duplicate resend refreshes mtime (`:89`), while ordinary reads do not. Boot and periodic GC remain active (`main.ts:726`, `attachment-gc.ts:13`).
3. Model history immediately loses the image after its send turn, even while that file remains readable: `toModelMessage` returns string user content (`turn-mapping.ts:95`). `media.get` exists for display, and the detached writer reads files; neither is a model-accessible exact-image recovery path.
4. Removing `image-description-writer` removes the only dedicated cross-turn visual-description producer. Its stated design is to outlive raw bytes, although actual episode retention is still governed by the selected Memory policy. Do not describe removal as preserving all visual memory: later requests retain only caption/[image], normal assistant statements and any independently written memories.
5. Automatic Local ingestion excludes user image parts entirely (`canonical-ingestion-source.ts:136`); an image-only user row supplies no speech text. Compaction receives text projections, including assistant speech, not the original visual details (`context-reduction.ts:121`). Changing foreground model selection does not change either contract.
6. Ambient `ScreenContext` is intentionally in-memory and only holds one description (`screen-context.ts:19`, `screen-context.ts:32`). It is not restored as usable Perception evidence after restart. Ambient and on-demand stores currently have no reader like the attachment store. Do not route an arbitrary saved local path as if it were a remote image URL.

### Minimal migration strategy

1. **Single main model.** Remove `visionModel`/`VisionDeps` selection, `loadVisionConfig`, its factory construction, bootstrap output and the four VLM knobs/UI entries. Keep `TAKI_PROVIDER_*`, utility text-processing ownership and existing main usage instrumentation. `config-source.ts:78` enumerates registered knobs, so obsolete stored VLM rows can remain inert for rollback; no destructive live config migration is necessary to hide/remove those consumers.
2. **One native message-building policy for proven images.** Reuse the existing `FilePart` builder and ordinary request path. Associate each image with its actual source: user row, exact completed screenshot result, or valid ambient/viewing capture. Use source/capture-time text beside pixels, keeping all capture results and untrusted-source meaning. Do not infer images from arbitrary third-party JSON keys.
3. **Screenshot follow-up.** Retain the true tool result metadata and store only trusted image references durably. At `ToolLoopAgent.prepareStep` (`agent-attempt.ts:101`), resolve completed capture material into native image parts in a provider-supported message role for the **next request**. The narrow default candidate is an app-supplied user message beside the faithful tool result, explicitly tied to its call ID. Verify ordering, role/source labels and no duplication across steps. Enable multipart tool-role output only when the applicable gateway contract is proved; do not stringify bytes. Cover captures through `extension_call` as well as the legacy `screenshot` tool: viewing code already invokes the former (`viewing-invitation-evidence.ts:81`).
4. **Native replay.** Reload retained user/capture refs for admitted model history, keeping bytes outside Timeline/Run durable rows. Include native image costs before admission or reselect/remeasure the full prepared request; hydrating after a text-only window selection alone undercounts history. Current estimates call the same `toModelMessage` projection (`conversation-store.ts:245`), so change the projection/measurement together. Preserve old text rows, call/result pairing, cancellation and source attribution. Missing, expired and invalid references must remain distinct from successful delivery. Exact raw visual recovery after TTL/clear is unavailable; that limitation needs an explicit acceptance contract.
5. **Ambient/proactive image material.** Change `ScreenContext` from description-only to a bounded latest-frame material with source epoch, capture time and valid lifetime. Extend the narrow turn/preparation input to carry native image material, not a base64 string embedded in `<turn-context>`. Preserve `perception.renderContext` for textual activity/source/time; supply the image beside it. Viewing `prepareInput` must return/attach image material to the admitted main request, because its present string return cannot deliver it. Do not spawn a main call solely to translate each sample. Cadence continues to capture under existing controls; the next eligible normal main request consumes valid evidence. If owner expects every ambient capture to trigger reasoning independently, that scheduling decision is additional to transport and must be explicit.
6. **Remove the translators together with their assumptions.** Delete `image-description-writer` and `screenshot-describe` producers/prompts, image Memory hook, `describe` dependencies, screenshot-only `describePrompt` behavior, VLM readiness checks, and `SENSITIVE_SCREEN` translation protocol. Update current contracts/headers rather than leaving statements that images never reach main. Keep historical descriptions and historical auxiliary usage readable.
7. **Keep real usage with no image category.** Attribute user images to user input, screenshot images to the associated tool evidence, and ambient/viewing images to injected current context. Modality can affect estimate coverage without becoming a separate composition bucket. Existing flat `IMAGE_TOKENS=1600` (`token-estimator.ts:42`) is a local estimate, not exact provider attribution. Native nested tool content would require part-aware estimation; its current `tool-result` branch prices JSON (`:65`). The user-message native projection avoids counting base64 as text. Preserve provider input/cache totals and single per-request usage correlation.

### Semantic and cost changes that require explicit treatment

- **Ambient semantic privacy is not just a prompt to delete.** The existing second privacy layer recognizes private content inside an otherwise allowed app (`sensitive-screen.ts:5`). `ambient-observation.ts:32` rejects the screen when the translator returns a sentinel. After eliminating the translator, separate pre-main semantic screening cannot remain that same independent model filter. Keep deterministic foreground/process/consent screening, and integrate any native-image semantic refusal, output restriction and discard behavior into the normal main decision. Do not claim the old semantic guarantee remains without a defined, tested replacement. This does not authorize keeping a translator.
- **`drop-after-describe` becomes a different lifecycle.** The default ambient retention removes bytes immediately after translation (`ambient-observation.ts:41`, `ambient-screenshot-config.ts:17`), and GC treats retained files as leftovers (`ambient-shot-gc.ts:25`). A captured image intended for a later main request needs a bounded in-memory/retained lease until consumption, expiry, replacement or retirement. Map existing public `drop` configuration explicitly to drop-after-consumption; retirement must still invalidate outstanding use. Keep ambient stores isolated from user attachments/on-demand screenshots (`ambient-shot-store.ts:15`).
- **Summary/Memory remain text systems unless deliberately changed.** Native recent replay preserves access only while raw files and relevant history remain available. It does not automatically preserve all visual facts after compaction or TTL. A generalized multimodal Memory/summary framework is unnecessary for this migration, but the accepted continuity boundary must be stated honestly.
- **Calls decrease, repeated input can increase.** Removing image/ambient/screenshot translators removes real model requests. Replaying pixels or injecting a fresh frame into each reasoning request can increase main input, affect prefix cache and change cost/latency. No percentage saving is established. Main images now use the main include-usage option; that does not prove the gateway reports all usage fields.
- **Accounting history must survive.** Auxiliary source enums and migration 065 include `image-description`/`screenshot-description` (`auxiliary-usage-schema.ts:15`, `065-auxiliary-model-usage.ts:15`). Removing active producers does not justify deleting historical labels/rows or rewriting recorded usage. Main and auxiliary request identities must not double-count an image call after migration.

### Complexity and task split

Changing only incoming user-image model selection is a small bounded change because native input already exists. The clarified deliverable is **a medium-to-large cross-layer migration**, not that small patch: it changes model/settings construction, tool-result delivery, native replay/admission, ambient state/privacy/retention, selected-initiative input and translation accounting. It can use existing stores, the SDK loop and current per-attempt material handling, without a new retrieval framework, general provider abstraction or second runtime.

Current context-attribution work should document modality coverage and classify delivered image material within existing categories. Implement the complete image transport/removal in the owner-directed separate child task, with one integrated review and validation. Do not make attribution depend on an unfinished rewrite, and do not use model-capability discovery as a reason to retain translators that the owner asked to remove.

## Caveats / Not Found

- No live main-model multimodal, multipart tool-role, semantic privacy, cost or owner manual acceptance was performed. Verify the selected native request shape against the actual supported route during implementation; do not make catalog integration a prerequisite or claim that every compatible endpoint supports all image roles/formats.
- `ToolMaterialSink` currently stores text/reference sidecars, not native image leases. The proposed per-step extension is a narrow candidate, not already implemented support.
- Full `extension_call` image-output serialization and all private-worker propagation were not independently traced in this report. The proven viewing consumer uses opaque capture output; implementation must trace its producer/adapters before claiming complete screenshot coverage. Coordinate with capability-discovery research instead of inferring an image from arbitrary JSON.
- Same-turn native input does not establish later exact visual recovery, permanent visual Memory, or summary quality. Native retained replay and expiry/compaction acceptance are required to make the removal reviewable.
- Removing every translator while keeping every previous ambient semantic/retention guarantee is not a pure deletion. Their actual replacement inside the normal main request remains a design/validation boundary; no hidden text bridge is recommended.
