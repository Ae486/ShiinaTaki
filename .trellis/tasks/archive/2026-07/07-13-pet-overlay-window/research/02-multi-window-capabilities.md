# Research: Multi-window setup + capability scoping (Tauri 2)

- **Query**: how to declare the pet overlay vs the existing default window vs future chat/settings windows; own label + own Vite HTML entry + own capability file; per-window capability scoping and the exact permissions a draggable transparent overlay needs
- **Scope**: mixed (repo state + installed capability schema)
- **Date**: 2026-07-13

## Findings

### Current repo state

- `apps/desktop/src-tauri/tauri.conf.json` declares ONE window (`app.windows[0]`), 480x640, `resizable:true`, opaque, **no explicit `label`** → Tauri defaults its label to `"main"`.
- `apps/desktop/src-tauri/capabilities/default.json` is the single capability file, `"windows": ["main"]`, permissions `["core:default","core:event:default","dialog:default"]`.
- Vite already does **multi-entry** rollup (`apps/desktop/vite.config.ts` L42-48): inputs `main` → `index.html`, `spike` → `spike.html`. Adding the pet overlay = add a third input (e.g. `pet` → `pet.html`) + its own React mount. This is the established pattern in-repo, not a new mechanism.

### How the three windows relate

Each Tauri window is `{ label, url, ...config }`. `url` points at an HTML entry served by Vite (dev) / bundled from `frontendDist` (prod). So:

| Window | label | HTML entry | capability file |
| --- | --- | --- | --- |
| existing default (pairing/status UI) | `main` | `index.html` | `capabilities/default.json` (exists) |
| pet overlay (this issue) | `pet` | `pet.html` (new Vite input) | new `capabilities/pet.json` |
| future chat/settings | `settings` etc. | own HTML entry | own capability file |

Windows can be declared statically in `tauri.conf.json` `app.windows[]` (created at launch) or built at runtime with `WebviewWindowBuilder`. For an always-present pet, static declaration is simplest.

### Tauri 2 capability model (verified against installed schema)

- Capability JSON files live in `src-tauri/capabilities/*.json`; each has `identifier`, `description`, a `windows` array (glob-matchable labels the capability applies to), and `permissions`. This is confirmed by the existing `default.json` and its `$schema` ref `../gen/schemas/desktop-schema.json`.
- **Per-window scoping is via the `windows` field.** A capability with `"windows": ["pet"]` grants its permissions only to the `pet` window; `"windows": ["main"]` (current) does not cover `pet`. So the overlay needs its own capability entry — it will NOT inherit `default.json`.
- The generated permission catalogue is `apps/desktop/src-tauri/gen/schemas/desktop-schema.json` (regenerated by `tauri-build`); permission identifiers below were extracted from it directly.

### Exact permissions a transparent draggable overlay needs (verified identifiers)

All present in the installed `desktop-schema.json`:

| Capability need | Permission identifier | Verified |
| --- | --- | --- |
| drag the borderless window (`startDragging`) | `core:window:allow-start-dragging` | ✓ |
| set position programmatically (persistence restore, manual drag) | `core:window:allow-set-position` | ✓ |
| read current position to persist | `core:window:allow-outer-position` / `core:window:allow-inner-position` | ✓ |
| toggle always-on-top at runtime (optional) | `core:window:allow-set-always-on-top` | ✓ |
| toggle decorations/shadow/skip-taskbar at runtime (optional; config covers launch) | `core:window:allow-set-decorations`, `core:window:allow-set-shadow`, `core:window:allow-set-skip-taskbar` | ✓ |
| resize/size at runtime (optional) | `core:window:allow-set-size` | ✓ |
| listen to window events (focus/blur/move — governor + persistence) | `core:event:default` | ✓ (event namespace) |
| **(issue #15, NOT this issue)** click-through | `core:window:allow-set-ignore-cursor-events` | ✓ (present, seam only) |

A minimal `capabilities/pet.json` for #14:
```jsonc
{
  "$schema": "../gen/schemas/desktop-schema.json",
  "identifier": "pet",
  "description": "Pet overlay window: drag + position",
  "windows": ["pet"],
  "permissions": [
    "core:event:default",
    "core:window:allow-start-dragging",
    "core:window:allow-set-position",
    "core:window:allow-outer-position"
  ]
}
```
(Add `core:window:allow-set-ignore-cursor-events` only when issue #15 lands — flagged as the seam, not designed here.)

### Architecture-invariant note (repo-specific)

CLAUDE.md invariant 4 says "Pet UI is a disposable client. Closing it must not affect agent sessions." Multiple windows each instantiate their own Zustand stores (`.trellis/spec/frontend/state-management.md`: "Each window (pet, settings) instantiates its own stores; cross-window sync goes through the Agent Core (WS events) or Tauri events — never assume shared JS memory between windows."). So the pet window is its own React root with its own WS/event wiring, not a component inside the main window.

## Caveats / Not Found

- Whether the existing `main` window (pairing/status) should be **merged into or kept separate from** the pet overlay is a product decision, not verified here. The pairing UI currently IS the default window; if the pet becomes primary, the pairing/status surface may move into a separate settings window. Flag for the leader.
- The `windows` field supports glob patterns (e.g. `"pet-*"`); exact glob semantics not re-verified against this schema version — confirm if you need wildcard scoping.
