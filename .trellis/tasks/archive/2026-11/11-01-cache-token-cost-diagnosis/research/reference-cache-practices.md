# Research: Reference cache and token-cost practices

- Query: Compare local pi and DeepSeek Harness mechanisms with TakiAgent's measured cache and additional token costs; identify provider-neutral options without weakening required behavior.
- Scope: mixed; local reference source, current installed SDK, and official provider/SDK documentation.
- Date: 2026-11-01
- Authorization: planning only. This file is the sole owned artifact; no reference/production code, data, configuration, processes, dependencies, or Git state were changed.

## Findings

### Decision summary

The references support measuring and reducing paid work per successful user task, rather than targeting a cache percentage in isolation. Preserve TakiAgent's existing canonical tools and stable-early/volatile-late prompt layout. The most useful additional candidates are compaction request reuse and failure accounting, task-appropriate tool-result reduction, and eliminating evidenced unnecessary continuations. None requires a provider-private caching API.

The parent investigator reported 263 cache-known requests, weighted cache-read/input of 68.4%, first primary requests of 48.82%, and in-run continuations of 97.24%. These figures are imported task evidence, not independently queried by this researcher. They show that the request groups differ materially; they do not by themselves identify a defective cache implementation. The reported 22 compaction failures and 85 avatar failures out of 163 avatar calls are investigation targets, not proof that every failure retried or incurred the same cost.

### Usage semantics: normalize before comparing

AI SDK 7.0.148 maps `inputTokens` from the provider total and exposes `inputTokenDetails.{noCacheTokens,cacheReadTokens,cacheWriteTokens}`; `outputTokenDetails.reasoningTokens` is a breakdown of total output (`packages/core/node_modules/ai/dist/index.js:2498`). The SDK sums these fields across steps in `addLanguageModelUsage` (`index.js:2532`). Mixing per-request rows with a run's `totalUsage` double-counts the same work.

The installed OpenAI-compatible adapter reads `prompt_tokens_details.cached_tokens` and `completion_tokens_details.reasoning_tokens`, subtracts cached input from total input, leaves cache-write unknown, and keeps raw usage (`packages/core/node_modules/@ai-sdk/openai-compatible/dist/index.js:40`). It defaults absent cached/reasoning details to zero. Consequently a normalized zero alone does not prove the provider reported zero; retain producer/field-coverage evidence. This adapter does not fall back to DeepSeek's separate `prompt_cache_hit_tokens` field in this converter, whereas the DSH adapter explicitly does (`llm-deepseek/src/translate.ts:53`). Current official DeepSeek wire docs expose both forms, so absence/mismatch in actual historical responses remains a coverage question, not a proved historical bug.

DSH rejects a summary that finishes at `max-tokens` with `MAX_TOKENS`, rather than committing a potentially incomplete checkpoint (`compaction-basic/src/summarizer.ts:206`). It only projects text into a checkpoint (`summarizer.ts:216`). These checks protect quality but also mean paid output can exist without a landed summary; increasing/decreasing a generation cap should follow the actual finish reason, token breakdown and checkpoint requirements, not a blanket cost budget.

DSH uses disjoint `inputTokens = prompt_tokens - cacheReadTokens` (`translate.ts:57`); pi's context accounting likewise sums input, output and cache buckets (`compaction.ts:146`). A DSH cache ratio denominator must add cache-read back to disjoint input. TakiAgent's inclusive input denominator must not add it again.

For DeepSeek wire input `I`, cache-read `H`, output `O`, and applicable per-million rates `r_miss`, `r_hit`, `r_out`, use:

`estimated_cost = ((I - H) * r_miss + H * r_hit + O * r_out) / 1_000_000`.

Reasoning is not an extra term when included in `O`. Missing usage, endpoint identity, historical tariff/time tier or currency makes this an incomplete estimate; no invoice dollar amount is established by the available task evidence. Other providers may bill cache writes differently, so this formula is a provider cost note, not a universal runtime contract.

### Official references, retrieved 2026-11-01

1. [DeepSeek Context Caching](https://api-docs.deepseek.com/guides/kv_cache): caching is automatic and best effort, with construction taking seconds and unused entries generally expiring within hours to days. Current documentation describes **SWA cache prefix units**, not unrestricted immediate reuse of every common prefix: units persist at input/output request boundaries, detected common prefixes and fixed intervals. Example `A+B`, then `A+C`, then `A+D` can have the second request miss before the newly detected `A` becomes reusable by the third. This is a plausible alternative explanation for first-request/continuation differences, not proof that those rules governed every historical row. The common prefix must still be identical; mid-input matches alone do not establish reuse.
2. [DeepSeek first-call / current model routing](https://api-docs.deepseek.com/): the legacy `/quick_start/pricing` URL returned this first-call page during retrieval. It states `deepseek-flash` currently routes to DeepSeek-V4.1-Flash-1017; retired `deepseek-v4-flash` and `deepseek-v4-flash-vision-exp` remain accepted and route to that model at Flash pricing. This is dated current routing evidence, not permission to merge all historical aliases or infer the exact backend checkpoint used by old requests.
3. [DeepSeek 2026-09-10 release announcement](https://api-docs.deepseek.com/news/news260910): announces V4.1-Flash and legacy Flash routing, with new pricing effective 2026-09-10 04:00 UTC and peak/off-peak pricing retained. Numeric tariffs are supplied in an image; this researcher did not verify those numbers. Provider tariff dates are not equivalent to a captured runtime endpoint/invoice.
4. [DeepSeek create-chat-completion wire contract](https://api-docs.deepseek.com/api/create-chat-completion): `prompt_tokens = prompt_cache_hit_tokens + prompt_cache_miss_tokens`; `prompt_tokens_details.cached_tokens` is the same cached count; `completion_tokens_details.reasoning_tokens` breaks down completion usage. `total_tokens` is prompt plus completion.
5. [AI SDK 7 migration guide](https://ai-sdk.dev/docs/migration-guides/migration-guide-7-0) and [streamText reference](https://ai-sdk.dev/docs/reference/ai-sdk-core/stream-text): SDK 7 removes old top-level `cachedInputTokens` / `reasoningTokens` in favor of nested details; cross-step totals must be distinguished from step usage. Context7 retrieval was checked against installed 7.0.148 source, which is the authority for this worktree.

### Actionable order and validation conditions

1. **Correct the measurement model first.** Group first primary requests, continuations, compaction, retries and background workers separately; preserve unknown fields and input/output overlap. Attribute billable work to successful user outcomes, with cache-hit/input as a secondary metric. Validation: complete request-level coverage and reconciliation without duplicate run/step totals.
2. **Investigate compaction's paid work and settlement.** For the reported failures, distinguish provider failure, output-limit/quality rejection, cancellation and retry; preserve known usage even if no checkpoint commits. Compare existing standalone and replay-shaped request layouts with isolated captured/synthetic inputs after implementation authorization. Validation: usable checkpoint, actual shrink, no orphan calls, no hidden loss of source facts, and total cost including failed attempts and the next primary request. A deterministic request-shape comparison is useful; paid experiments are not authorized now.
3. **Target large, redundant tool results before generic history pruning.** Use actual tool-size/call evidence to choose compact result views and recovery retrieval. Validation: same task completion/requirements, explicit truncation states, original evidence recoverable, and fewer total paid input/output tokens across follow-up retrievals. A higher cache rate is not required if the smaller result costs less.
4. **Challenge repeated failed or purely presentational loops.** Map reported avatar validation failures to emitted tool feedback and subsequent requests, rather than assuming every failure is an execution retry. Validation: no repeated impossible call without new information; task result, presentation delivery and feedback remain correct. Do not solve by disabling required tools, hiding errors or imposing an arbitrary step cap.
5. **Retain stable-prefix invariants and explain invalidators.** Regression checks should keep semantic system/tool values stable across new internal identities and within-run requests append-only, while recording expected compaction, generation, persona, date and replay-window changes. Official SWA/warm-up/expiry behavior remains an unmeasured provider condition; it must not become a production vendor branch or a fabricated causal label.

## Caveats / Not Found

- Source reading and official documentation retrieval establish mechanisms, not live performance or quality acceptance. No LLM calls, build/test execution, dependency installation or data changes were performed.
- Reference sources may contain changes absent from an earlier public release; the versions above describe the local checkout, not a claim of production behavior in TakiAgent or an upstream tag audit.
- No raw conversation or secret was copied. The parent owns actual database/scenario measurements and will resolve the imported figures against its evidence.
- Prefix-unit availability, expiry, model checkpoint, exact historical endpoint, account tariff and invoice currency were not captured in these reference findings. Current public model aliases cannot retroactively prove every request's backend identity.
- pi's standalone summary path and DSH's replay-shaped path disagree deliberately. Neither is universally optimal; inherited instructions, tools, source privacy, summary quality, warm-prefix availability and retry costs determine applicability.
- Whole-history persistence, provider cache-retention controls, DSH private attribution headers, model changes, required-tool removal and arbitrary token/loop limits are outside the accepted optimization scope.
