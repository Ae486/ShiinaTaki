## Intended experience

Taki is the user-facing Companion and an assistant capable of coordinating permitted operations. External media services own deterministic platform extraction, Cookie handling, subtitles, frame sampling and provider calls. Under M20, Taki may diagnose failures and coordinate recovery across available Execution Hosts; ordinary credential synchronization should run without a model decision or secret values entering conversational context.

Three scenarios are in scope:

1. **Co-Watching**: three entry paths converge on the same accepted task: detected viewing, an explicit user request, or a Taki-selected OpenBili recommendation (M52). Detected viewing first passes deterministic eligibility before lightweight Agent judgment; it does not start detailed analysis merely because a video is open. The recommendation path may pre-analyze selected videos under M53. Co-Watching acceptance is required before Character commentary generation under M54. The media service supplies complete structured, approximately timed content; Taki uses the normal Agent and Skill to prepare optional Character-voiced candidates. Actual playback and current interaction rules control delivery. Accepted-task speech follows M51, while unsolicited invitations retain proactive rules. Contextual controls distinguish direct viewing from Co-Watching, with Stop available once Co-Watching is accepted. Useful content may remain unspoken, inform a later response, or support an optional closing reflection.
2. **Media acquisition and understanding**: analyze supported video links and user-provided local video files, summarize their content and answer questions through the service boundary (M29). Reuse BiliNote's video-upload input while implementing the necessary governed file transfer. Analysis input alone does not provide a live playback clock; exact user-facing download/artifact delivery behavior remains to be specified.
3. **Discovery and personalization**: use OpenBiliClaw's content discovery, recommendations, user profile and native feedback learning. Retain an OpenBili browsing surface inside Taki independently of the smaller set Taki selects for proactive Co-Watching (M57-M58). Ordinary recommendation browsing does not submit every displayed video for BiliNote analysis.

#### Representation and ownership

Keep three distinct resources: a session-owned commentary plan with editable candidates; an immutable snapshot selected for one delivery; and the resulting publication/presentation evidence. A candidate is one independently editable, optional utterance. It may combine several analysis moments; it is neither a mandatory response to a moment nor an already-spoken assistant message. Keep the existing Viewing Moment term for upstream content evidence. Proposed commentary terminology remains local to this design until agreed.

| Resource / field group | Proposed contents and purpose |
| --- | --- |
| Plan identity | Core-owned `planId`, active Co-Watching `sessionId`, exact media/part identity, Character identity and upstream analysis reference/version. These bindings are not editable model-authored identifiers. |
| Plan revision | A monotonically increasing authoring revision for atomic update batches. Playback ticks do not change it. First use one serialized session writer and optimistic revision checks; a distributed editing protocol is unnecessary. |
| Candidate identity | Stable `candidateId` and a Core-incremented content revision. Rewording or retiming preserves the logical identity; replacing an old object with a new ID must not reset delivery history. |
| Content and intent | The prepared text, a short purpose/topic description when useful, and referenced source moments. Topic/provenance help Taki select related candidates when dialogue changes; they are not proof of semantic deduplication. |
| Playback timing | An earliest eligible time, preferred time and latest timely time in media milliseconds. Enforce ordering and media-duration bounds when known. The preferred time is an opportunity; current interaction rules can still suppress it. |
| Reveal boundary | Earliest permissible disclosure derived from the referenced content and reviewed wording. Moving a candidate earlier also requires reviewing its content. A timestamp or model-provided tag does not prove that its wording is spoiler-free. |
| Optional presentation intent | Character-appropriate semantic expression information, resolved/validated against current presentation capabilities when needed. Text and optional voice share one content revision; no future direct animation commands execute during drafting. |
| Runtime-owned evidence | Cancellation/session generation, current dialogue validation, claimed content revision, publication identity, transport result and any actual rendering/audio evidence. The model cannot set these fields or declare a candidate delivered. |

Each candidate should normally make sense on its own. Avoid references such as "as I said earlier" unless the referenced statement was actually published and the current interaction supports that wording. This keeps a skipped or withdrawn candidate from invalidating a scripted chain. First use source/topic references and small related batches instead of building a general dependency graph.

#### Local edits and dialogue integration

Propose one main Core-local authoring operation, provisionally `update_commentary_plan`, with bounded `add`, `replace` and `withdraw` operations. `replace` provides a complete replacement for one candidate's editable fields rather than string offsets into a long script; retiming is a replacement subject to the same checks. Several withdrawals/additions/replacements may form one atomic batch for merging or splitting candidates. Preserve their source/lineage references and already-published coverage.

The command includes an expected plan revision and idempotent mutation identity; Core binds the authenticated Character, session, caller Run/Attempt and observed dialogue generation. It validates the whole batch, verifies targets remain editable, and commits all changes together or returns a conflict/no-longer-editable result without partial changes. A repeated mutation does not add duplicates. Never silently overwrite a newer plan or reapply a stale model patch to a different session. The result reports actual changed IDs and the new revision so Taki knows whether its edit took effect. This is an informational authoring operation, not an Avatar presentation tool.

Recommended conversation flow:

1. A new user interaction immediately holds new timed output under P06, before model interpretation finishes. Do not pause the user's video as a side effect. Retire any obsolete delivery binding while retaining the editable plan content.
2. Give the normal dialogue turn a bounded current-plan view: upcoming candidate details, a compact future outline, actual publication references and the relevant upstream moments. Read additional candidates on demand for broader changes; do not insert the full script into every dialogue turn or label pending text as conversation history.
3. Taki answers the user and, where relevant, proposes a local edit. Unrelated dialogue can leave content unchanged; broad requests such as "less teasing, more explanation" can affect the remaining plan. This does not require a second conversational Agent or a model invocation on every playback tick.
4. Follow M41 when releasing timed output: retain the plan when no edit was requested, without a separate whole-plan review; withhold candidates affected by required, pending or failed edits. Unknown edit impact temporarily withholds all timed commentary, not ordinary conversation. Only Core may establish current delivery bindings, and an invalidated old delivery never resumes merely because an edit failed. Keep user-reply latency separate from a large optional rewrite.
5. Re-evaluate timing when a patch commits and again at dispatch. An edit that arrives too late does not create a catch-up burst. Material can remain available for later synthesis or a new valid opportunity under P02/M16.

Skills specify content selection, Character voice, restraint, source use, spoilers and when to edit or remain silent. The Core tool/service owns the candidate data and applies edits. The playback/delivery path owns timing, current-state checks, cancellation, budget and publication. Upstream BiliNote/OpenBili services continue owning analysis and their own job/result lifecycle. #### Dispatch, interruption and consistency

Treat plan mutation and dispatch commitment as competing operations on the same candidate revision. Before final commitment, an accepted edit or withdrawal invalidates older prepared payloads and any derived assets. If dispatch has already committed, the published version is immutable; a late patch must report that it could not retract it. A local claim is not evidence that presentation already occurred. Recheck revision/session/dialogue eligibility after asynchronous preparation and at the last dispatch boundary, and propagate revocation to any client-side queue. Once output is in flight, cancellation can stop remaining work but cannot guarantee that nothing was already seen or heard.

Keep publication and observation separate. Record the exact content revision, Timeline reference and transport/presentation result; a successful tool response, queued message, socket write or render report is not proof the user heard a complete utterance. Preserve unknown outcomes and suppress automatic duplicate replay. Do not implement network exactly-once delivery by retrying blindly or rewriting conversation history after an uncertain send.

Missed timing and permanent withdrawal are different: forward-seek skips that passage's opportunities; a previously unspoken, still-valid candidate may be considered after a rewind under P02. Already-published commentary is not repeated merely because of a rewind, content edit or new ID. If ordinary dialogue already expressed the same point, use that actual dialogue evidence to withdraw/adjust the overlapping candidate. Stop, media/part changes or Character/session invalidation retire the old plan's future activity; late edit, analysis and asset callbacks cannot reactivate it.

Persist pending candidates as labeled domain work, separate from conversational utterances. Authoring tool-call/result evidence still follows the existing full-turn persistence contract; do not delete tool records to hide draft creation. Current plan snapshots should override stale draft descriptions as the source of planned content. This does not claim atomic removal of material already consumed by the model or extend M28 into summary/history rollback. Full Core restart continues to follow M36/M37 and T4-D85; a saved plan alone does not establish safe resumability.

Optional TTS preparation must be keyed to candidate/content revision and the applicable voice settings. An edit invalidates an older synthesized clip, and late synthesis completion is checked again before presentation. Near-term preparation can avoid synthesizing every far-future draft; timing remains anchored to media progress. Existing TTS material is a reserved design, not verified current audio support or a new prerequisite for this integration.

OpenBiliClaw does not have to run entirely on the user's desktop. Its extension supports a remote backend, HTTPS and device pairing. ### Automatic synchronization and Taki recovery coordination — 2026-10-02

Source findings, rechecked without real credentials or deployment tests:

- OpenBiliClaw already synchronizes Bilibili credentials at extension startup, on relevant Cookie changes, on periodic alarms and on `bilibili_cookie_sync_requested` events (`extension/src/background/cookie-sync.ts:321,706,803,814,908`). The preferred new API is `POST /api/sources/bilibili/credential`. Browser synchronization copies the current session; it does not itself renew an expired platform login.
- BiliNote's [readBrowserCookies/syncCookieToBackend](https://github.com/JefferyHcool/BiliNote/blob/90940fde4d224d0f69ad99674f4af0a1ea52d3c4/BillNote_extension/src/logic/cookies.ts#L20) already provide browser collection and upload, called by its settings page. Automatic triggers, protected cross-service delivery and downloader credential reload remain integration work. A successful configuration write is not sufficient recovery evidence.
- Taki's existing [Run assembly](../packages/core/src/extensions/extension-run-context.ts) includes Host-qualified capabilities, and its [capability router](../packages/core/src/capabilities/route-capability.ts) accepts explicit `targetHostId` and rejects ambiguous legacy routing. [Host Context](../packages/core/src/hosts/host-context.ts) publishes availability and explicit-target rules. These are reusable coordination primitives, not proof that media recovery helpers or both deployed Hosts are ready.

The proposed recovery sequence implements M19-M20; exact adapters and contracts remain design work:

1. Distinguish missing/expired credentials from remote network/risk-control failures. Pause only credential-dependent work and retain the reason and recovery need; do not repeatedly ask for login when the actual failure is VPS access.
2. When the bound browser source becomes available or its login changes, automatically request its current credential under the established service/account binding. Validate from the target service environment, apply to each intended consumer, and verify readiness separately for OpenBiliClaw and BiliNote. Retry transient delivery failures with bounded backoff.
3. If the browser still has a valid session, this path needs no manual Cookie copying. If it requires sign-in or a platform challenge, surface the relevant browser interaction; successful login should trigger synchronization and revalidation automatically.
4. If deterministic recovery cannot finish, Taki may inspect sanitized status, diagnose the available Hosts, request synchronization, open the appropriate setup/login entry or invoke a supported reload/repair operation under the existing governance. A local-acquisition/VPS-analysis fallback is a possible strategy only after its transfer path is implemented and permitted.
5. Keep actual credential collection and delivery in trusted components, using a protected destination-bound channel. Taki reasons over account identity, credential presence/version and operation results; secret bytes must not enter model context, ordinary tool output or the normal Host-control channel. This is compatible with Host-local credential storage and does not make general artifact transfer a secret-export capability.
6. Host connection, browser/extension readiness, platform login validity and User Presence are separate signals. A connected desktop Host can permit background synchronization without proving that the user can currently complete a visible login flow. A disconnected Host cannot execute recovery commands.
7. Reconnect reconciliation and fresh synchronization are new operations against current state under current authority, not blind replay of interrupted Host mutations. Credential recovery does not reopen explicitly stopped Co-Watching, replay stale speech or establish that an interrupted analysis job completed.

Account-switch behavior is settled by M21: validate a stable platform account identity before applying an automatic update; a nickname or Cookie presence is insufficient. A same-account refresh can proceed automatically. A different account is a binding mismatch requiring an intentional switch, not permission to replace the current credential. If the original credential still works, mismatch alone need not suspend its service; if it has expired, M19 applies. Explicit rebinding does not by itself authorize deleting old data or combining another account's profile; the relevant data policy remains to be specified.

### Non-branching cancellation and invitation latency — 2026-10-02

The owner's cancellation concern is about future model context and speculative outputs, not just wasted analysis computation. Distinguish these boundaries:

- Backend completion can precede bridge receipt, artifact storage, model consumption and user-visible delivery. A result can arrive after Stop if the backend could not cancel; that does not authorize injecting it into the ended session.
- An input already sent to an in-flight model cannot be removed from that inference retrospectively. Its continuation can be aborted or discarded. Stronger context reconstruction could omit that session's material, but M28 deliberately starts without conversation branching or historical cleanup. A cancellation reminder does not guarantee that raw or derived content already in replay has been forgotten.
- Ending a session withdraws its material's eligibility for that interaction; it does not establish that the underlying video analysis is factually false. Artifact retention and future explicit reuse are separate from automatic context reuse.

Selected first design under M28; not implemented or runtime-tested:

1. Keep the existing conversation instead of creating or switching a conversation branch. Retain enough media-session/Run identity to target cancellation and reject late output; identity and stale-result guards do not themselves require a fork.
2. 3. Automatically insert a trusted cancellation notice addressed to Taki, even if no analysis result has arrived. Make it available before the next relevant model request; an already-running inference is interrupted rather than assumed to receive a new message mid-request. The notice is runtime context, not a fabricated user utterance, and need not force Taki to speak an acknowledgement.
4. Continue the same conversation with its existing history. Do not add automatic history deletion, rolling-summary reconstruction, memory rollback or a hidden replacement conversation to simulate a fork. Material already read or persisted may still influence subsequent requests; evaluate that explicitly.
5. Keep backend analysis cancellation under M25: attempt cancellation where practical, otherwise allow completion without reactivating Co-Watching. A late result is not a new invitation or permission to continue an unfinished utterance. A later explicit user question about the video is a new request.

Illustrative model-facing notice, not a finalized wire schema: "The user cancelled Co-Watching session {sessionId} for {mediaId}. Stop this session's reasoning and pending commentary. Do not continue unsent drafts or resume the session when analysis results arrive. Handle a later explicit question about the video as a new request."
