## 3. Mission and Dependency Order

T4 turns the Companion runtime into a truthful autonomous execution surface. The central abstraction is an Autonomous Run: a Core-owned, inspectable execution with an initiator, immutable effective context, one or more Attempts, explicit terminal state, and optional user-facing delivery.

The dependency order is mandatory:

    Autonomous Run + Run Receipt
              |
              +-- Scheduled Task trigger
              |
              +-- Heartbeat trigger
              |
              +-- common delivery / retry / offline / approval semantics
              |
              +-- later Procedural Knowledge and Experience Review

Do not build separate execution loops for Scheduled Tasks and Heartbeat. Both enter the same Run/Attempt lifecycle and reuse the existing Agent runtime through additive seams.

### 3.1 In scope

- Core-owned Run and Attempt records, lifecycle transitions, provenance, terminal outcomes, and queryable receipts;
- five semantic turn initiators: primary, heartbeat, scheduled, flush, and subagent;
- deterministic scheduler and persisted schedule definitions;
- Heartbeat Class B eligibility and delivery;
- Scheduled Task Class A behavior;
- ordinary timeline delivery for spoken proactive output;
- Home projection of schedules and Run state;
- provider-neutral Memory Context and commitment queries needed by T4;
- D59 transport-liveness acceptance where required for reliable delivery.

### 3.2 Not part of the first T4 task

- a second permission or Approval system;
- a new Skill format or Skill-carried permissions;
- literal reminder delivery that bypasses an Agent Run;
- hidden synthetic user rows in the relationship timeline;
- automatic application of Experience Review proposals;
- automatic authority switching between Local and Hindsight Memory;
- Heartbeat as WebSocket keepalive, ping/pong, or scheduler tick;
- scenario-specific Main Model slots;
- broad memory redesign beyond T4's provider-neutral seams;
- D60 web search redesign.

## 5. Frozen Product Contracts

The following were resolved by the owner. Do not ask them again unless new evidence proves the contract impossible or unsafe.

### 5.1 Identity and persistence

- characterId owns the continuous relationship timeline.
- taskId owns one Scheduled Task definition.
- runId owns one Autonomous Run and is its resume/query key.
- attemptId distinguishes retries inside a Run.
- Run initiator and content provenance are separate and never inferred from each other.
- Every claimed Scheduled execution and every eligible Heartbeat Agent run writes internal Autonomous Run History.
- Only actual Companion speech enters the relationship timeline.
- User-expected background work normally projects a structured Run Receipt into Home, linked by runId.
- Silent and avatar-only Heartbeats create no fake user row and no visible empty conversation turn.
- An SDK sessionId, if required, maps to an existing relationship or Run identity; it is not another history authority.

### 5.2 Initiators and delivery classes

| Concept | Meaning | Must not be confused with |
| --- | --- | --- |
| primary | ordinary user-originated turn | Scheduled Task or Heartbeat |
| heartbeat | no-user-message Class B judgment | network heartbeat |
| scheduled | a Scheduled Task fire, normally Class A | literal alarm delivery |
| flush | internal maintenance/flush turn | user-visible autonomy |
| subagent | delegated execution | content provenance |
| Class A | deterministic, user-expected trigger | Heartbeat budgets |
| Class B | autonomous judgment, silence normal | permission level |

The class is decided when output is created, not at delivery time.

Class A is not counted against Class B budgets. Quiet hours hold/release expected work under the schedule contract. Class B has strict budgets, suppression, minimum gaps, and ignore-backoff.

### 5.3 Scheduled Task

- Every fire starts a restricted scheduled Autonomous Run. No literal reminder bypass exists.
- Canonical schedule forms are at, every, and cron. Natural-language understanding belongs to the creating Agent; persisted forms are deterministic.
- Persist the source wall-clock pattern and timezone policy. nextRunAt is derived and recomputed on restart or User Timezone change.
- Catch-up is fixed: one-shot cutoff 24 hours; recurring cutoff half the period; missed work coalesces once and is marked late.
- Provider/model failure is a truthful retryable Run outcome, never silent success.
- Pause, resume, edit, and delete are durable operator mutations.
- Scheduled Tasks serialize per Character, cannot recursively schedule, and leave structured evidence.

### 5.4 Heartbeat

- Heartbeat is a no-user-message LLM turn and Class B judgment, not transport liveness. It may be armed by an
  approximate cadence or by a meaningful normalized external/internal Signal.
- A raw signal never calls the model directly. Signal Providers normalize observations, then deterministic freshness,
  dwell, dedupe, debounce/coalescing, cooldown, optional deterministic chance, privacy, busy, quiet-hours, and budget
  rules decide whether Wake Policy admits a Run.
- Periodic and event-driven sources converge before `TriggerRequest`; both reuse `RunService -> ChatAgent` and the
  existing Run/Attempt/Event/Effect authorities.
- Deterministic pre-checks eliminate empty/no-due/no-new-signal calls before invoking the model.
- Heartbeat v1 may use narrow Core reads, relevant Skills, already-eligible context, and Companion presentation.
- It does not use exec, acquire fresh sensors outside the Sampling eligibility path, or cause external side effects.
- An ask action skips quietly and records why. It never opens a surprising unattended dialog.
- Silence is structural: heartbeat_respond is the terminal response path. No normal sentinel is required.
- heartbeat_respond needs a dedicated terminal stop condition.
- Starting calibration is configurable: approximately 15-minute eligibility beats, hard cap 4 beats/hour, maximum 2 delivered utterances/hour and 8/day, 10-minute minimum gap, quiet hours 23:00-08:00, busy deferral maximum 90 seconds, stale utterance TTL 10 minutes.
- These are development defaults, not immutable constants.
- Pure no-reason companionship is out of v1. A meaningful typed signal is required.

#### Interaction Pattern and Companion evolution

- Taki's product goal is not only automation: Heartbeat supports a Companion that appears to notice, form bounded
  judgments, and interact in a Character-consistent way. The concrete wording, expression, and decision to remain
  silent are generated per Run rather than stored as fixed response templates.
- Keep the Character Soul/Persona stable. User/relationship models, bounded Companion State, one-shot intentions, and
  Interaction Patterns may evolve; autonomous growth must not rewrite the Soul Prompt or core safety policy.
- The existing typed Core-owned Heartbeat checklist evolves into the Interaction Pattern authority rather than
  creating a second strategy/runtime system. A Pattern contains trigger conditions, interaction purpose, context
  references, `silent | express | speak` outcomes, cooldown/cadence/expiry, optional chance, origin/provenance/evidence,
  revision, and `proposed | active | paused | retired` lifecycle. It contains no fixed dialogue.
- `intention` remains a one-shot unspoken thought that expires or is consumed. A recurring Interaction Pattern is a
  reusable habit; transient thoughts must not silently become permanent rules.
- Shipped, user-authored, and Agent-proposed Patterns use one typed Core store and API shared by the panel and Agent.
  A Pattern-authoring Skill teaches the Agent how to propose/revise patterns but grants no permission and cannot write
  the database, runtime code, Persona, or safety prompt directly.
- User/relationship graphs are projected into small provider-neutral context summaries; Heartbeat does not load an
  entire graph or compile facts directly into executable rules.
- New wording or pattern combinations should normally require data/Skill changes only. A new signal source requires a
  Signal Provider, a new expressive/OS action requires a governed Capability, and new safety limits require Runtime
  code and tests.
- Heartbeat implementation must reserve origin/provenance/revision/state, feedback association, rollback, context
  seams for user model/relationship model/Companion State/intentions, and Run evidence for matched Signals/Patterns and
  selected outcome. Default behaviors are seed data, not engine branches.
- Full Companion State/self-model learning and feedback-driven long-term Pattern evolution may ship in later bounded
  slices, but their reserved seams must remain in the global plan. A first Heartbeat batch is not the final design.
- Long-lived Agent-authored Patterns default to reviewable candidates. Any future opt-in automatic activation remains
  bounded by limits, version history, and one-click rollback; it is not implicit permission to self-modify.

### 5.5 User Timezone

- Core owns one persisted IANA User Timezone.
- It has fixed mode or follow-primary-device mode.
- VPS process-local time is never user authority.
- A schedule may pin its own IANA timezone; an absolute instant remains UTC.
- User Timezone changes recompute future due times and do not blindly replay an old backlog.

### 5.6 Memory

- T4 uses the provider-neutral Memory Context and Memory Tool Contract.
- It must not import legacy Markdown storage, a Local-only MemoryRepo, or tidy.maybeRun() directly.
- Local and Hindsight adapters expose the same T4-facing contract.
- Authority never silently switches during an outage.
- Pending Memory may be used as explicitly unconfirmed context. Pending status alone neither wakes nor suppresses Heartbeat.
- Non-primary turns never run conversational auto-memory or advance episodic/flush watermarks.
- Memory Replica synchronization is internal maintenance, not a Scheduled Task, Heartbeat, delivery class, or Agent-editable row.

### 5.7 Privacy, Approval, and Hosts

- Privacy Pause applies according to acquisition source and delivery class; it is not a blanket mute for all Class A or Core-only paths.
- Perception stays scrubbed and fenced through the sanctioned system/Replay View seam.
- Core remains the single Governance/Approval authority.
- Do not add Heartbeat permission pages, Scheduled Task permission tables, Task Archetypes, or parallel Approval stores.
- Heartbeat skips ask actions. Scheduled work may expose a resumable waiting-for-authorization Run Receipt.
- Host availability is planning context, not permission.
- A Run may finish Core work before a Host step, fail an unavailable Host action, or request bounded wait-for-user where the common operation contract allows it.
- Disconnected Host work is never silently substituted or replayed.
- Reuse host-operation-lifecycle.md for every Host-bound action.
- D59 sleep/resume and half-open detection retire the old generation through the existing reconnect system. They never start an Agent Heartbeat.

### 5.8 Delivery

- Spoken proactive output uses the ordinary timeline append path.
- Do not create proactive.* protocol methods or a third delivery authority.
- A proactive message appears whole in the Pet bubble, never as private stream deltas.
- Pet restoration follows the guarded per-generation timeline path.
- Home and Pet must agree on the spoken text.
- Reconnect must not replay stale presentation.

### 5.9 Procedural Knowledge

- Procedural Knowledge belongs to the applicable Skill, Scheduled Task, or capability guidance, not Long-term Memory.
- Run evidence may include loaded Skill identity/hash, tools, failures, retries, provider/model, and verification.
- Experience Review requires a high-value signal such as corrected verified success, a user correction, a demonstrably wrong Skill, a verified non-trivial procedure, or repeated workarounds.
- v1 may create a pending Learning Proposal but never changes live behavior without owner review.

## 9. Minimum Acceptance Matrix

### Run and Receipt

- one Run has one immutable snapshot and ordered Attempts;
- terminal settlement is idempotent;
- cancelled, failed, completed, skipped, waiting, and outcome_unknown remain distinct where applicable;
- stale responses cannot mutate newer generations or replay effects;
- every autonomous result is queryable by runId;
- a Run Receipt is evidence, not a synthetic user message.

### Scheduler / Class A

- one-shot, recurring, timezone, and DST behavior are deterministic;
- catch-up uses the 24-hour/half-period rule, coalesces once, and records late;
- every fire starts a scheduled Run;
- provider/model failure is visible and retryable within its deadline;
- Agent tool, Core, and Home observe the same schedule rows and next-run state.

### Heartbeat / Class B

- empty/no-due/no-new-signal pre-check makes zero model calls with a named skip reason;
- silence and avatar-only outcomes create no visible empty turn;
- spoken output creates one ordinary assistant timeline path and one whole Pet bubble;
- busy user work wins; deferred output is latest-wins, bounded, and stale-discarded;
- quiet hours, caps, gap, and ignore-backoff are independently testable;
- malformed or non-terminal output fails quiet without leaking private prose.

### Memory and Privacy

- Local/Hindsight context is provider-neutral;
- non-primary turns do not advance conversational auto-memory;
- Pending Memory follows ADR 0009 and G2-08;
- Privacy Pause and stale observation bleed-out remain correct;
- sensed/external content stays scrubbed and fenced;
- unattended work never opens an unexpected Approval dialog.

### Reliability and UI

- Host generation loss settles without replay;
- half-open and sleep/resume restore through D59;
- Pet and Home agree on spoken output;
- Core/provider/Pet/Home absence produces truthful state;
- manual residuals are recorded as observed, unobserved, or unavailable.
